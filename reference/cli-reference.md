## Условные обозначения

- Все команды имеют префикс `chloros-cli`. На Windows бинарный файл имеет имя `chloros-cli.exe`; на Linux /Jetson — `chloros-cli`.
- Необязательные аргументы показаны в виде `--flag`. Обязательные позиционные аргументы указаны без скобок.
- Если задан значение по умолчанию, при пропуске флага используется именно это значение.
- CLI — это «тонкий» клиент HTTP, работающий через бэкенд Chloros (сервер Flask на `127.0.0.1:5000`). Бэкенд запускается автоматически при выполнении большинства команд. `CHLOROS_BACKEND_URL=<url>` направляет семейства команд **`lattice`**,**`project`**и**`daq pool-*`** на удалённый бэкенд — основные команды (`process`, `login`, `logout`, `status`, `export-status`, `time-sync`, `selftest`) намеренно фиксируют `http://127.0.0.1:<port>` и игнорируют его (литерал IPv4 предотвращает штраф в размере ~2 с на запрос в «Windows» `localhost`→`::1`, что приводит к потере ~2 с на каждый запрос). См. [Переменные среды](#environment-variables).
- Для всех вызовов SDK / CLI требуется вход в систему с учётной записью Chloros+ (запускайте `chloros-cli login` один раз на каждом компьютере; кэшируется в `~/.chloros/`).
- В примерах используются пути Linux; на Windows замените `/home/user/...` на `C:/Users/.../...`.

## Обзор верхнего уровня

```
chloros-cli [global options] COMMAND [command options]
```

| `--port N` | Порт бэкэнда HTTP (по умолчанию: `5000`). |
| `-v, --verbose` | Включить подробный вывод. |

## Установка

`chloros-cli` поставляется в составе установщика Chloros для настольных компьютеров на всех поддерживаемых платформах — отдельной загрузки CLI нет. Установка пакета для платформы добавляет `chloros-cli` в ваш `PATH` наряду с настольным приложением и бинарным файлом бэкенда , который он управляет.

Последние версии для скачивания: [`https://mapir.gitbook.io/chloros/download`](https://mapir.gitbook.io/chloros/download)

> Установщик также содержит удобные скрипты запуска (`Chloros_CLI.bat` / `Chloros_CLI.ps1`, `Launch_CLI.*`, `chloros-cli.sh`), которые открывают готовую к использованию оболочку CLI; они описаны в [Руководстве пользователя CLI](../CLI.md) и не дублируются здесь.

### Установщик «Windows» (.exe)

1. Загрузите установщик Windows со страницы загрузки.
2. Запустите файл `Chloros-Setup-x.y.z.exe` и следуйте инструкциям мастера установки. Путь установки по умолчанию — `C:\Program Files\Chloros\` (CLI помещается в папку `C:\Program Files\Chloros\cli\`, которую установщик добавляет в переменную PATH).
3. Откройте новый терминал (`cmd.exe`, PowerShell, или терминалWindows), чтобы была использована обновленная версия `PATH`.

```powershell
chloros-cli --version
```

Установщик автоматически добавляет `chloros-cli.exe` в системную среду `PATH` и включает в него среду выполнения Arena SDK, необходимую для камер LATTICE.

### Linux amd64 (.deb)

Для Ubuntu 22.04 LTS или более поздних версий / рабочих станций на базе Debian с архитектурой x86_64.

> **Ubuntu 20.04 не поддерживается.** Список зависимостей пакета составлен на основе
> того, с чем фактически связывается бэкенд, и в него входит `libc6 (>= 2.34)`;
> focal поставляется с glibc 2.31. `apt` отказывается от установки, вместо того чтобы допустить сбой
> во время выполнения.

```bash
sudo dpkg -i chloros-amd64.deb
sudo apt-get install -f         # only if dpkg reports missing dependencies
chloros-cli --version
```

Пакет .deb устанавливает:
- `chloros-cli` до `/usr/bin/chloros-cli`
- Скомпилированный бэкэнд до `/usr/lib/chloros/chloros-backend`
- Среду выполнения Arena SDK (для камер LATTICE)
- Модели шумоподавителя, пакеты калибровки и конфигурацию канала обновлений

### Linux arm64 — Jetson (JetPack 6)

```bash
sudo dpkg -i chloros-arm64-jp6.deb
sudo apt-get install -f
chloros-cli --version
```

Такая же структура, как у .deb-пакета для amd64, с сборкой CUDA, оптимизированной для Jetson Orin / Orin NX / Orin Nano.

### Однократная аутентификация на каждом устройстве

На каждой платформе требуется однократный вход по адресу Chloros+ перед тем, как начнут работать вызовы SDK / CLI:

```bash
chloros-cli login user@example.com 'YourPassword'
```

Учетные данные кэшируются в `~/.chloros/user_session.json`.

### Проверка установки

```bash
chloros-cli --version           # prints "Chloros CLI 1.2.0"
chloros-cli selftest            # full 7-step diagnostic (backend, GPU, models, CUDA)
chloros-cli status              # shows license tier + logged-in user
```

> **Требуется подписка на Chloros+.**Для работы CLI требуется активный тарифный план Chloros+.**Copper**— это базовый уровень Chloros+; каждый платный уровень Chloros+ предоставляет доступ к CLI / SDK; только бесплатный уровень**Iron** не предоставляет такого доступа. (Соответствие идентификаторов тарифных планов: `0`=Iron/free, `1`=Copper, `2`=Bronze, `3`=Silver, `4`=Gold.) Повышение уровня на [`https://cloud.mapir.camera/pricing`](https://cloud.mapir.camera/pricing).
>
> Этот нижний предел обеспечивается на стороне сервера, а не только в файле CLI: запрос с флагами SDK / CLI без оплаченного тарифного плана отклоняется с кодом `403 PLAN_UPGRADE_REQUIRED`, независимо от того, поступает ли он из `chloros-cli`, Python SDK или из самодельного клиента HTTP. Вызванный, не вошедший в систему, получает вместо этого код ошибки `401 AUTH_REQUIRED`. Доступ работает в автономном режиме в течение льготного периода тарифного плана (30 дней для месячного плана, до истечения срока действия для годового) и прекращается по истечении этого срока; код `chloros-cli status` продолжает работать, чтобы причина была видна (это единственный маршрут SDK / CLI, освобожденный от ограничения по уровню — `GET /api/license-status`).

## Пятиминутное краткое руководство

```bash
# 1. Sign in once on this machine
chloros-cli login user@example.com 'YourPassword'

# 2. Survey3 / LATTICE folder → finished radiance + NDVI in one call
chloros-cli process "/home/user/captures/flight_001" \
  --vignette --reflectance --indices NDVI NDRE GNDVI

# 3. Take a single LATTICE photo with the first camera found
chloros-cli lattice capture -o output/

# 4. Connect a 4-cam LATTICE array with the GUI's smart-prep flow
chloros-cli lattice array-connect \
  --serials 213800234,214000533,214701288,214701292

# 5. Read a spectrum from a connected DAQ-U
chloros-cli daq pool-connect --port COM3
chloros-cli daq pool-latest --sensor-id CB-7C-A8-2E-5F   # id from 'daq pool-list'
```

## `chloros-cli process`

Обработайте папку с изображениями через полный конвейер Chloros (обнаружение цели → калибровка → виньетирование → отражательная способность → экспорт индекса).

### Краткое описание

```
chloros-cli process INPUT [OPTIONS]
```

### Позиционные аргументы

| Аргумент | Описание |
| --- | --- |
| `INPUT` | Путь к входной папке, содержащей файлы `.raw + .jpg` (Survey3), `.tif/.tiff` (LATTICE) или `.dng`. |

### Общие параметры

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `-o, --output PATH` | новая папка с меткой времени в пути к проекту по умолчанию (`~/Chloros Projects`, если не настроено иначе) | Папка проекта для создания или повторного использования. Если в папке уже находится файл `project.json`, вместо перезаписи создается файл-аналог `_1`/`_2` вместо перезаписи. |
| `-n, --project-name NAME` | auto (отметка времени) | Название проекта. |
| `--debayer {standard,texture-aware}` | `standard` | `texture-aware` использует нейронный дебайер Chloros+; работает медленнее, но обеспечивает более высокое качество. |
| `--vignette / --no-vignette` | `--vignette` | Коррекция виньетирования. |
| `--reflectance / --no-reflectance` | `--reflectance` | Калибровка отражательной способности (использует калибровочную панель, если она найдена, или серийную калибровку NIST для LATTICE). Для мультиспектральных данных LATTICE это также служит переключателем **продукта** отражательной способности — см. [Переключатели экспорта по продуктам](#per-product-export-toggles-lattice-multispectral). |
| `--ppk` | выкл. | Применить корректировки PPK GNSS из файлов sidecar. |
| `--exposure-pin-1 MODEL` | выкл. | Закрепить модель «pin-1» для установки с двумя камерами «Survey3». |
| `--exposure-pin-2 MODEL` | выкл. | Закрепить модель «pin-2». |
| `--recal-interval SECONDS` | 0 | Принудительно пересчитывать калибровочные вычисления каждые N секунд времени съёмки. |
| `--timezone-offset HOURS` | локальный | Переопределить смещение часового пояса, заложенное в выходные метаданные. |
| `--format FORMAT` | `TIFF (16-bit)` | Один из следующих: `TIFF (16-bit)`, `TIFF (32-bit, Percent)`, `PNG (8-bit)`, `JPG (8-bit)`. |
| `--indices NAME [NAME ...]` | none | Индексы растительности (`NDVI`, `NDRE`, `GNDVI`, `EVI`, `SAVI`, `OSAVI`, `CIG`, …). |
| `--input-level {auto,raw,debayered,processed}` | `auto` | Принудительно устанавливать точку входа в конвейер для файлов LATTICE TIFF (файлы Survey3 с расширением .raw не затрагиваются). Также предусмотрен «аварийный выход», позволяющий обрабатывать записи с **без исходных данных** — см. [Как выглядит папка с захватами](#what-a-captures-folder-looks-like). |
| `--debayered / --no-debayered` | включено | Выводить результат линейного дебайерирования (`Debayered_Images`). См. [Переключатели экспорта для отдельных продуктов](#per-product-export-toggles-lattice-multispectral). |
| `--preview / --no-preview` | включено | Выводить предварительный просмотр (`Preview_Images`): RGB = баланс белого (источник освещения DAQ, если доступен, в противном случае — «серый мир») + гамма; multispec = растяжение в ложноцветном режиме. |
| `--radiance / --no-radiance` | включено | Вывод значения яркости в формате float32 (`Radiance_Images`, Вт/м²/ср/нм). |
| `--reflectance-source {daq,target,auto}` | `auto` | Эталон для продукта отражательной способности LATTICE: `auto` = цель в кадре, прошедшая контроль качества (QA), является абсолютным эталоном; в качестве резервного варианта используется нисходящее излучение DAQ (ρ = π·L/E); `target` = строгий (без замены данными DAQ); `daq` = авторитетные данные DAQ. См. [Переключатели экспорта по продуктам](#per-product-export-toggles-lattice-multispectral). |
| `--target-reflectance-dir DIR` | нет | Каталог сканов **измеренного** отражательного коэффициента цели для каждой единицы (`<serial>.csv`); при отсутствии данных используется резервный вариант — номинальные спектры T3/T4P. |
| `--array-alignment / --no-array-alignment` | включено | Массивы LATTICE: применять выравнивание «модуль к модулю», отмеченное в каждом снимке`Chloros:Alignment*` XMP к каждому обработанному продукту (дебайеризованный / предварительный просмотр / яркость / отражательная способность / индекс). Не выполняется для изображений без этих тегов. |
| `--array-alignment-crop / --no-array-alignment-crop` | crop | Обрезать выведенные данные, выровненные по массиву, до общейобласть перекрытия, чтобы все модули занимали одну площадь; `--no-…` сохраняет полную область датчика (заполнение чёрным за пределами исходного изображения). |
| `--array-alignment-interp {bilinear,nearest,cubic}` | `bilinear` | Передискретизация для деформации при выравнивании. `nearest` сохраняет точные значения DN источника (без смешивания радиометрических значений между пикселями). |

### Параметры обнаружения целей

| Флаг | Описание |
| --- | --- |
| `--min-target-size PIXELS` | Минимальный размер панели-цели (px) для детектора. |
| `--target-clustering 0-100` | Чувствительность кластеризации. |
| `--target / --targets` | Рассматривать входную папку как только панель целей (пропустить обнаружение обзора). |

### Примеры

```bash
# Simplest: defaults are good for most surveys
chloros-cli process "/home/user/images/survey_001"

# Multi-index with explicit format
chloros-cli process "/home/user/images/survey_001" \
  --vignette \
  --reflectance \
  --format "TIFF (32-bit, Percent)" \
  --indices NDVI NDRE GNDVI OSAVI

# Texture-aware debayer for highest quality (Chloros+ only)
chloros-cli process "/home/user/images/survey_001" \
  --debayer texture-aware \
  --indices NDVI

# Process LATTICE captures explicitly (auto-detects from EXIF normally)
chloros-cli process "/home/user/captures/lattice_flight" \
  --input-level processed

# LATTICE multispectral → float32 radiance only (no DAQ downwelling needed)
chloros-cli process "/home/user/captures/lattice_flight" \
  --no-debayered --no-preview --no-reflectance

# LATTICE reflectance anchored to an in-frame target (strict, no DAQ fallback),
# with per-unit measured target scans looked up by serial
chloros-cli process "/home/user/captures/lattice_flight" \
  --reflectance-source target --target-reflectance-dir "/home/user/target_scans"

# LATTICE array capture: keep native geometry (ignore stamped alignment)
chloros-cli process "/home/user/captures/array_flight" \
  --no-array-alignment

# Aligned, uncropped, value-preserving resampling
chloros-cli process "/home/user/captures/array_flight" \
  --no-array-alignment-crop --array-alignment-interp nearest

# Save to a custom output location with a project name
chloros-cli process "C:/input" -o "C:/output" -n "Field_A_2026-05-26"
```

### Переключатели экспорта для отдельных продуктов (LATTICE multispectral)

Обработка LATTICE разветвляется на **все применимые продукты за один проход**. Четыре переключателя для отдельных типов — `--debayered`, `--preview`, `--radiance`, `--reflectance` —**по умолчанию включены**; используйте форму `--no-<type>`, чтобы отключить один из них. Главные камеры RGB всегда выдают только данные после дебайеризации + предварительный просмотр (без данных о яркости/отражательной способности по отдельным полосам), поэтому для них переключатели `--radiance`/`--reflectance` не действуют. Переключатели игнорируются для Survey3 `.raw` (которые следуют стандартному пути «отражательная способность/цель»). *(Старый флаг `--radiometric-output {reflectance,radiance,sensor-response}` был **удален** и заменён этими переключателями; уровня `sensor-response` больше нет.)*

| Продукт | Выход | Требуется ли нисходящий поток DAQ? |
| --- | --- | --- |
| `--debayered` | Линейная демозаика (`Debayered_Images`). | Нет. |
| `--preview` | Предварительный просмотр (`Preview_Images`): RGB = WB + гамма; multispec = растяжение в ложных цветах. | Нет. |
| `--radiance` | float32 Вт/м²/ср/нм из полной радиометрической цепочки (`Radiance_Images`). | № |
| `--reflectance` | uint16 коэффициент отражения ρ (`32768` = 1,0), готово к использованию в Pix4D. | **Да**, если только она не привязана к прошедшему контроль качества объекту в кадре (см. ниже). |

`--reflectance-source` выбирает эталон отражательной способности:**`auto`**(по умолчанию) делает цель в кадре, прошедшую контроль качества,**абсолютным эталоном**— цепочки эмпирических линий, привязанные к мишени, подвергаются перекрестной оценке на отложенных панелях, и применяется измеренный победитель — с переходом к даунвеллинговому делителю DAQ (ρ = π·L/E), если мишени нет или QA не прошла;**`target`**является строгим (без замены данными сбора данных);**`daq`**переключается на поведение, определяемое DAQ. Геометрия цели (ArUco / фиксированная область интереса / полоса) берется из конфигурации цели проекта; `--target-reflectance-dir DIR` хранит**измеренные** сканы для каждого устройства (`<serial>.csv`), которые ищутся по серийному номеру/QR-коду целевого устройства, а в качестве резервного варианта используются номинальные спектры T3/T4P.

Путь отражения DAQ автоматически определяет **нисходящее излучение с совпадающей временной меткой**на основе записанного**`.daq`**(DAQ-U/M/E)**или из собственного файла DAQ-M `.csv`**, находящегося рядом с изображениями. Если пакет калибровки для конкретной камеры или DAQ не кэширован локально, конвейер**автоматически загружает его из AWS** при первом использовании (требуется однократное подключение к Интернету; кэшируется под именем `~/.chloros/`).

#### Чтение пикселей отражательной способности (Pix4D / Metashape / ваши собственные скрипты)

Отражательная способность хранится в виде целого числа DN, и **значение DN, соответствующее ρ = 1,0, зависит от исходной камеры**:

| Источник | ρ = 1,0 соответствует | Как определить |
| --- | --- | --- |
| LATTICE (M3C / M3M) | `32768` (запас до ρ 2,0) | В файле проставлен штамп XMP `Chloros:PixelScale=32768`. |
| Survey3 | `65535` (обрезано при ρ 1,0) | Отсутствие тегов XMP `Chloros:*` — именно это *и* является признаком. |

**Считайте значение `Chloros:PixelScale` и делите на него**, а не принимайте за постоянную величину. Тег определён в области uint16, поэтому он остаётся неизменным `32768` при изменении масштаба выходных форматов — `TIFF (16-bit)`, `PNG (8-bit)`, `JPG (8-bit)` и `TIFF (32-bit, Percent)` — все они самоописывающиеся (сначала нормализуйте хранящийся тип данных обратно в uint16: ×257 из 8-битного, ×65535 из float).

> **Один случай по замыслу не предусматривает масштабирования.** Когда данные, полученные из 8-битного источника (BayerRG8), записываются в формате 8-битного TIFF, конвейер *обрезает* значения до диапазона 0..255 вместо перемасштабирования, поэтому каждое значение выше ρ≈0,008 сглаживается до 255, и файл не описывает масштаб. Chloros намеренно опускает там как `Chloros:PixelScale`, так и кортеж `MicaSense:RadiometricCalibration`, и фиксирует в журнале причину. **Если тег отсутствует в файле отражательной способности LATTICE, не следует предполагать наличие масштаба — переэкспортируйте в 16-битном или 32-битном формате**, вместо того чтобы делить пиксели, которые никогда не были делимы.

#### EXIF, переносимый при экспорте

`process` копирует **GPS-блок и его ExifIFD** в каждый продукт, поэтому
экспорт содержит `FocalLength`, `FNumber`, `ExposureTime`, `ISO`, `DateTimeOriginal` и
`CameraSerialNumber` наряду с геореференцированием.

**`FocalLength` не является опциональным для фотограмметрии.** Pix4D рассчитывает расстояние между точками на местности на основе
фокусного расстояния и высоты над землей; при отсутствии тега программа использует крайне неверный масштаб. В ходе одного
полете над апельсиновой рощей с 49 снимками отсутствие этого тега превратило участок размером 411 м × 160 м в реконструированный
47,8 км × 13 км — ортофотоплан объёмом 455 МП, состоящий в основном из «nodata», что впоследствии было расценено как проблема с мозаикой и
проблема с BigTIFF, прежде чем кто-либо проверил GSD. Если ваш ортофотоплан получается в неправдоподобном
масштабе, сначала запустите `exiftool -FocalLength` над экспортированным продуктом.

Копия намеренно **не** является `-all:all`: структурные теги IFD0 нарушают вывод LATTICE при
копируются, а `ExifImageWidth` / `ExifImageHeight` исключены, поскольку они описывают
*исходную* съемку — в противном случае экспорт, размер которого когда-либо изменялся, содержал бы размеры,
противоречащие его собственному растру. Файл XMP записывается напрямую, а не копируется, поскольку ExifTool
отбрасывает теги XMP, созданные в рамках одного вызова, при копировании блока XMP (что привело бы к потере тегов калибровки MAPIR
).

### Где сохраняются результаты

Результаты записываются **в папку проекта, сгруппированные по камерам, а затем по форматам файлов**:

```
<project>/
└── LATT-M3M-L41-F550/                  # one folder per camera model+lens+filter
    ├── tiff16/
    │   ├── Reflectance_Calibrated_Images/
    │   ├── Debayered_Images/
    │   ├── Preview_Images/
    │   └── <INDEX>_Index_Images/        # e.g. NDVI_Index_Images
    └── tiff32/
        └── Radiance_Images/             # float32 radiance always lands here
```

Папка камеры для LATTICE — `LATT-<sensor>-<lens>-F<filter>` (соответствующая EXIF снимка
`Model`), а для Survey3 — `<model>_<filter>` — две камеры, использующие один и тот же сенсор и фильтр, но имеющие разные
объективы, хранятся в отдельных деревьях, поскольку у них различаются виньетирование, поле зрения и искажения. Папка формата
имеет следующий вид: `--format`: `tiff16`, `tiff8`, `png8`, `jpg8` или `tiff32` для
`TIFF (32-bit, Percent)`.

> **Каждый экспортированный продукт сохраняет имя исходного файла.** Экспорт из Radiance файла
> `capture_…_raw.tif` по-прежнему называется `capture_…_raw.tif` — он просто находится в
> `tiff32/Radiance_Images/`. **Продукт идентифицируется по папке, а не по имени файла**, поэтому поиск по шаблону
> `*radiance*.tif` ничего не найдёт; вместо этого используйте сопоставление по каталогу.

### Записи датчика освещённости — откалиброванные `.daq` + `.csv`

`process` также обрабатывает записи `.daq` в вашем входном папке, и для этого ему **не**
требуются никакие изображения: DAQ-U / DAQ-M / DAQ-E, запущенный самостоятельно, представляет собой полноценный
устройство сбора данных, а папка, содержащая только файлы `.daq`, является допустимым входным материалом.

Запись с DAQ можно вести **без** его калибровки — именно это по умолчанию делают общедоступные
[`chloros_scripts`](https://github.com/mapircamera/chloros_scripts)
(`record_daq.py`) по умолчанию: они записывают необработанные данные датчика и помечают файл таким образом, чтобы
Chloros извлекал заводскую калибровку этого датчика **по серийному номеру** (сначала из локального кэша,
затем из облака MAPIR) и применяет её. `process` записывает результат обратно:

```
<project>/
└── Light Sensor/
    ├── <name>_calibrated.daq        # reprocessable archive, declares its bundle
    └── <name>_calibrated.csv        # W/m^2/nm per reading + photometric columns
```

Файл `.csv` содержит по одной строке на каждое измерение: метка времени UTC, время интегрирования, общая мощность,
фотопические/скотопические люксы, PPFD (и его разбивка по синему/зелёному/красному), пиковая длина волны, а затем
полный спектр по собственной сетке длин волн датчика. `.daq` повторно импортирует данные без
повторной калибровки.

В случае успеха запуск сообщает `Light-sensor products written: N (calibrated .daq + .csv)`.
Текст в скобках описывает, что было фактически записано, поэтому он выглядит следующим образом:
`(RAW COUNTS — this sensor has no calibration bundle)` для датчика без пакета и
`(N calibrated, M raw counts)` для папки, содержащей и то, и другое. Собственные заголовки бэкенда
`[DAQ-EXPORT]` и `[RUN-SUMMARY]` — формируются таким же образом: ни один из
этих трёх не может называть необработанный экспорт «откалиброванным».

Запись DAQ-U / DAQ-M / DAQ-E, для которой невозможно получить пакет калибровки — вы
находитесь в автономном режиме или для данного датчика в файле отсутствует калибровка — **пропускается с указанием причины** в строке
`[DAQ-EXPORT]`; она никогда не записывается как «откалиброванный» файл, содержащий необработанные отсчёты.
Подключитесь к Интернету и запустите процесс заново. Причина — это та, которую система фактически
установил для этого файла (нечитаемая схема, отсутствие пакета, ошибка записи), а в сводке
запуска перечислены **отдельные** причины — двадцать файлов, пропущенных по одной причине, отображаются как одна
причина, а не как двадцать повторений этой причины.

#### Экспорт записей DAQ-A в виде необработанных отсчетов

Семейство **DAQ-A** появилась до внедрения системы пакетов для каждого серийного номера и не имеет калибровочного пакета
для загрузки — вместо этого она калибруется в полевых условиях по мишени отражения, поэтому
в ней никогда не было необходимости в пакете. Отказ от этих записей лишал пользователей возможности
получить их данные вообще, поэтому они экспортируются под **другим именем**:

```
<project>/
└── Light Sensor/
    ├── <name>_raw.daq        # NOT _calibrated
    └── <name>_raw.csv        # raw spectral sensor counts, NOT irradiance
```

Используется другое имя файла, а не флаг внутри файла, поскольку информация о записи должна сохраниться
передачи по электронной почте в виде простого имени. Заголовок `.csv` указывает
`raw spectral sensor counts (NOT irradiance)` и предупреждает, что значения сопоставимы
**в пределах** пределов файла — именно для этого они и используются при калибровке по целевому объекту — а
не между датчиками. Зависимые от мощности фотометрические столбцы (общая мощность, фотопические и
скотопические люксы, PPFD) записываются как **NULL**, а не интегрируются из числа импульсов, и в сводке
прогона указано `RAW COUNTS`, поэтому «экспортированные» в журнал данные нельзя интерпретировать как интенсивность излучения.

Старые записи **v1.01 / v1.02** (их записывает DAQ-A-SD) не содержат эпохи для каждого отдельного считывания,
только время записи файла. Модуль сопоставления изображений↔нисходящего излучения по-прежнему их отклоняет — сопоставление
кадра со временем записи привело бы к незаметной ошибке — но экспортер их считывает, и
CSV выводит `clock=daq_created_on`, поэтому в названии продукта указывается, на каком часовом интервале он находится.

### Примечания

- `process` автоматически определяет, является ли ваша папка папкой типа «Survey3», «LATTICE» или смешанной.
- Ход выполнения передаётся через Server-Sent Events; на странице CLI отображается текущий прогресс по каждому потоку (обнаружение, анализ, обработка, экспорт).
- Для устройств Linux /Jetson утилита CLI проверяет объём подкачки и может выдать предупреждение перед обработкой больших папок. Дебейер с учётом текстур также автоматически применяет ограничение частоты GPU на энергоэффективных устройствах Jetson (Nano, Orin Nano).
- В случае успеха запуск сообщает, сколько изображений было записано (`Image products written: N`).

#### Запуск, в ходе которого не было записано ни одного изображения, завершается с ошибкой

Если вы запросили результаты, а запуск не записал **ни одного** — только `project.json` и
`calibration_data.json` — `process` рассматривает это как сбой: он выводит
`Processing finished but wrote no image products.` и **завершает работу с кодом ненулевым**, так что скрипт может
это обнаружить. В сообщении указана папка проекта и обычные причины:

- входная папка не была распознана как съёмка (проверьте структуру и `--input-level`), или
- все запрошенные продукты были пропущены как неприменимые для этих камер (например, запрос на
  измерение радианции/отражательной способности с камер, поддерживающих только режим «RGB»).

Запустите программу заново с параметром `--verbose` и проверьте журнал бэкэнда на наличие строк `[LATTICE-EXPORT]` / `[EXPORT-CHECK]`,
которые объясняют пропуски по отдельным камерам, которые иначе не попадают в вывод CLI.

Намеренный запуск «только с метаданными» — при отключенных всех продуктах и отсутствии `--indices` — по-прежнему считается
**успешным**, поскольку пустой вывод изображений в данном случае является правильным результатом.

То же самое относится и к **запуску «только с датчиком освещенности»**: папка с записями `.daq` по определению не содержит изображений для экспорта,
и запуск оценивается по откалиброванным файлам `.daq` / `.csv`, которые были записаны вместо этого.

## `chloros-cli login`

Аутентифицируйте это устройство с помощью учётной записи облачного сервиса Chloros+. Учётные данные надёжно кэшируются в файле `~/.chloros/user_session.json`.

```
chloros-cli login EMAIL PASSWORD
```

### Примеры

```bash
chloros-cli login user@example.com 'YourPassword'

# Passwords containing $ should use SINGLE quotes
chloros-cli login user@example.com 'my$ecret$pass'
```

> **PowerShell `$$` mangling is auto-corrected.** In double quotes PowerShell expands `$$` (удаляя или дублируя части пароля). При ошибке 401 CLI автоматически повторяет попытку, добавляя в конец `$$`, а затем с-дублированной половиной пароля; если повторная попытка завершается успешно, вас авторизуют и выведут правильный синтаксис с одинарными кавычками для использования в следующий раз.

> **Использование без графического интерфейса/в скриптах: отсутствие кэшированной сессии означает интерактивный приглашение к вводу, а не быструю ошибку.** Любая команда, запускающая бэкенд (`process`, `status`, `export-status`, `time-sync`, …) , запущенная без кэшированной лицензии/сессии, перед продолжением работы выводит интерактивный запрос `Email:` / `Password:` в стандартный ввод (stdin). Поэтому автозадача без кэшированной сессии зависнет в ожидании ввода — запустите `chloros-cli login EMAIL PASSWORD` один раз на каждом компьютере перед планированием заданий в режиме без интерфейса.

## `chloros-cli time-sync`

Состояние и управление PTP-грандмастером. На хосте Chloros запущен PTP-грандмастер; устройства LATTICE cams и DAQ-E работают в режиме подчинения для синхронизации временных меток между устройствами.

| Подкоманда | Описание |
| --- | --- |
| `status` | Показать состояние главного сервера, приоритеты BMCA, идентификатор тактового генератора. |
| `peers` | Вывести список подчиненных устройств, обнаруженных через Delay_Req (камеры + датчики DAQ-E). |
| `cameras` | Состояние PTP для каждой камеры (`PtpStatus`, `PtpOffsetFromMaster`, `PtpMeanPathDelay`). |
| `restart` | Перезапуск процесса «grandmaster». |
| `set-priority --priority1 N --priority2 N` | Переопределение приоритетов BMCA. |

### Примеры

```bash
chloros-cli time-sync status
chloros-cli time-sync peers
chloros-cli time-sync cameras
chloros-cli time-sync restart
chloros-cli time-sync set-priority --priority1 1 --priority2 1
```

## `chloros-cli lattice`

Управление камерой LATTICE. Каждая подкоманда проходит через бэкенд Chloros; этот бэкенд владеет пулом камер, поэтому последующие вызовы CLI повторно используют тот же открытый дескриптор.

### Общие параметры (общие для большинства подкоманд)

| Флаг | Описание |
| --- | --- |
| `-d, --device N` | Индекс камеры (по умолчанию: 0). |
| `-s, --serial SN` | Конкретный серийный номер; переопределяет `--device`. |
| `--serials SN1,SN2,…` | Серийные номера, разделенные запятыми, для работы с несколькими камерами. |
| `--all` | Работать со всеми обнаруженными камерами. |
| `--exposure US` | Время экспозициив микросекундах. |
| `--gain DB` | Коэффициент усиления в дБ. |
| `--pixel-format FMT` | например,g. `BayerRG8`, `BayerRG12`. |
| `--width N` / `--height N` | Размеры изображения. |
| `--preset {default,high_quality,high_speed,triggered}` | Применение предустановки параметров. Все режимы свободного хода, за исключением `triggered`, который переводит камеру в режим ожидания аппаратного сигнала по линии 2 — если на эту линию ничего не поступает, камера будет ждать бесконечно, а не производить захват. |
| `-o, --output DIR` | Каталог вывода (по умолчанию: `output`). |
| `--packet-size {auto,jumbo,standard,N}` | Размер пакета GVSP. `auto` запускает пробы ICMP+GVSP; `jumbo` = 9000; `standard` = 1500. |

### Рабочий процесс первого подключения камеры LATTICE

```bash
# 1. Discover cameras on the network
chloros-cli lattice info

# 2. Single-cam smoke test: capture one frame.
#    By default this saves EVERY export type applicable to the cam
#    (raw, debayered, radiance, reflectance, preview). Pass e.g.
#    `--processing debayered` to save just one.
chloros-cli lattice capture -o output/

# 3. Connect a synchronized array (RECOMMENDED ENTRY POINT for arrays).
#    This is the same "smart-prep" flow the Chloros GUI uses:
#      - Network capability probe (ICMP DF ping + GVSP probe)
#      - Tier auto-pick (sim-emit / ftd-stagger / slip)
#      - Auto-shrink frame size to fit the wire
#      - PTP enabled by default
#      - Per-cam pixel format auto-pick
#      - AE seeding from the cam's saved state
#      - GPIO trigger config on Line2
chloros-cli lattice array-connect \
  --serials 213800234,214000533,214701288,214701292

# 4. Capture one synced frame group from the live array.
#    Defaults to --processing all (one file per export type per cam);
#    pass a single level to narrow it, e.g. --processing reflectance.
chloros-cli lattice array-capture --processing reflectance -o output/

# 5. Live-preview one cam in your browser
chloros-cli lattice viewer --serial 213800234

# 6. Tear down when done
chloros-cli lattice array-disconnect
```

### Справочник подкоманд

#### Обнаружение и информация

| Подкоманда | Назначение |
| --- | --- |
| `lattice info` | Вывести список подключённых камер (производитель, модель, серийный номер, IP, MAC). |

| `lattice network-analysis --master SN --slaves SN1,SN2,… [--width N] [--height N] [--pixel-format FMT] [--binning N] [--force-tier TIER] [--backend-url URL] [--json]` | Сетевые возможности бэкенда со стабильной схемой + рекомендации по массивам (возвращает `status` ∈ `ok` / `auto_shrunk` / `auto_capped_fps` / `needs_force_slip` / `error`). `auto_capped_fps` сохраняет запрошенное разрешение, но ограничивает целевую частоту кадров — считывает значение `recommended.recommended_target_fps` и передает его в качестве цель подключения; рассматривайте это как успех, а не как ошибку. |
| `lattice analyze-array [--models M1,M2,…] [--binning N] [--n-active N] [--width N] [--height N] [--pixel-format FMT] [--force-tier TIER] [--json]` | Анализ «что, если» без запуска камер. **`--n-active` — это общее количество камер в сети, а не только в этом массиве**— генерируйте это сообщение, когда автономные камеры передают поток одновременно, или когда бюджет кабеля рассчитывается исходя из спроса, в котором их количество занижено (по умолчанию: `len(--models)`). Всегда выводит совокупные значения строк `Wire budget:` (требуемая пропускная способность в МБ/с по сравнению с безопасным для предотвращения коллизий пределом) и строки `Max cameras:`, а также устанавливает флаг `** OVER-SUBSCRIBED**`, когда массив перегружает канал — см. [Частота кадров массива и модель всплеска](#array-fps--burst-model). |
| `lattice gpu` | Показать состояние графического процессора. |
| `lattice firmware [--update] [--force] [-y\|--yes]` | Проверить или обновить прошивку камеры. Локальный выбор `.fwa` зафиксирован: файл в `firmware/<MODEL_PREFIX>/`, соответствующий `MIN_FIRMWARE_VERSION` сборки, записывается в ПЗУ при наличии (только самая последняя версия в качестве резервного варианта), поэтому более новый образ поставщика, подготовленный на диске, остается неактивным до тех пор, пока этот фиксированный параметр не будет изменен — более новые версии целенаправленно поступают на устройства через подписанный манифест AWS, что предпочтительнее, если версия более новая. |
| `lattice presets [--apply NAME]` | Просмотр или применение предустановок камеры. |
| `lattice status` | Состояние камеры в реальном времени. |

| Подкоманда | Назначение |

#### Индекс / Математика растительности

```bash
# Offline: compute NDVI from an aligned multi-band TIFF
chloros-cli lattice index --input aligned.tif --preset NDVI \
  --output ndvi.tif --colorize --gradient RdYlGn

# Live: discover array, calibrate alignment, capture, compute index, in one go
chloros-cli lattice index --live --profile align.json --preset NDVI \
  --save-multiband -o output/
```

Полный набор флагов: `--input PATH | --live --profile PATH`, `--preset NAME` (NDVI / NDRE / EVI / SAVI / GNDVI /…), `--formula EXPR`, `--channel SYM=BAND` (повторяемо), `--capture-level raw|debayered|radiance|reflectance|unknown` (переопределить уровень захвата, записанный в исходном файле TIFF; по умолчанию: считывается из метаданных TIFF), `--output PATH`, `--output-format all|raw|tif|colorized|lut|png`, `--gradient NAME|JSON`, `--vmin/--vmax/--percentile LO,HI`, `--bg-mode clip|transparent|indexColor|backgroundColor`, `--colorize`, `--list-presets`, `--list-gradients`. При использовании `--live` также применяются регуляторы искажения выравнивания: `--save-multiband`, `--gpu/--no-gpu`, `--no-crop`, `--bit-depth 8|12|16`, `--vignette`, `--interpolation nearest|linear|cubic|lanczos`, `--border-mode constant|replicate|reflect|wrap`, `--border-value N`.

> **В символах `--channel` учитывается регистр.** Название символа должно точно совпадать с названиями каналов пресета (в пресетах используется строчный регистр, например, NDVI = `red`, `nir` — проверьте `--list-presets`), а сторона диапазона должна совпадать с именем диапазона в выровненном стеке (или быть индексом полосы с нулевым началом в автономном режиме). `--channel red=Red_660 --channel nir=NIR_850` работает; `--channel RED=660` завершается с ошибкой `channel_map missing entries`.

##### Параметры `array-connect`

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `--serials SN1,SN2,…` | Автоматическое обнаружение всех камер LATTICE (требуется ≥2) | Первая по порядковому номеру камера является MASTER. Если этот параметр опущен, обнаружение фильтруется по моделям LATTICE (`TRI032*`) и подключает все из них. |
| `--line {Line0,Line2,Line3}` | `Line2` | Линия синхронизации GPIO. |
| `--target-fps F` | auto | Частота срабатывания триггера MASTER. |
| `--force-tier {sim-capture-sim-emit, sim-capture-ftd-stagger, slip-emit-and-capture}` | auto | Переопределить выбор уровня. |
| `--wire-ceiling-mbps MB_PER_S` | auto-detected | **Устойчивый бюджет пропускной способности хоста, в МБ/с — от этого значения зависит выделение ресурсов для всего массива.** Уменьшайте его, если массив сообщает о кадрах с повреждением GVSP: значение «auto» рассчитывается на основе объявленной скорости связи сетевой карты, которая завышает показатели для USB-адаптеров, узких линий PCIe и загруженных общих магистралей. Это значение сохраняется в блоке захвата массива проекта, поэтому его восстановление происходит при повторном открытии / CLI / SDK. См. [Состояние массива](#array-health--which-subsystem-is-losing-frames). |
| `--binning {1,2,4}` | auto | Аппаратное биннирование. |
| `--no-recommend` | off | Пропустить этап анализа сети. |
| `--no-ptp` | off | Отключить PTP (в этом случае временные метки между камерами **не** будут сопоставимы). |

### Smart-AE / Smart-Capture

Массивы LATTICE запускают непрерывную автоэкспозицию (AE) в фоновом режиме сразу после подключения, но длянаведенная сцена требует некоторого времени для сходимости. `array-capture --smart` представляет собой **удобное решение**: он дожидается, пока AE стабилизируется на всех камерах в массиве, а затем запускает съёмку. Используйте его при смене сцены в середине сеанса.

```bash
# Connect once, then take settled captures whenever you re-point the rig
chloros-cli lattice array-connect --serials SN1,SN2,SN3,SN4
chloros-cli lattice array-capture --smart --processing reflectance -o pose_a/
# (move the rig)
chloros-cli lattice array-capture --smart --processing reflectance -o pose_b/
```

По умолчанию политика стабилизации является консервативной: таймаут 5 с, окно стабильности 1,5 с, ±5 % допустимое отклонение экспозиции. Настройте параметры через конфигурационный файл «SDK» (`ArrayHandle.capture_smart(settle_timeout_s=…, stability_window_s=…, exposure_tolerance_pct=…)`), если вам требуется иное поведение автоматизации.

### Уровни экспорта снимков (по умолчанию — `all`)

Начиная с данного выпуска, `lattice capture`, `lattice multi-capture` и `lattice array-capture` **по умолчанию настроены на `--processing all`** — по одному сохраненному файлу на каждый тип экспорта, применимому к каждой камере, что соответствует поведению функции «Захватить всё» в графическом интерфейсе пользователя. Уровни:

| Уровень | Выход | Применимо к |
| --- | --- | --- |
| `raw` | Одноканальный Байер (для монохромных камер: одна полоса) напрямую с датчика. | Все камеры. |
| `debayered` | 3-канальная демозаика BGR (для монохромных камер: 1-канальный в оттенках серого). | Все камеры. |
| `radiance` | float32 Вт/м²/ср/нм через полную радиометрическую цепочку. | Только мультиспектральные (M3C/M3M) — **пропускается для камер с фильтром «RGB»**. |
| `reflectance` | uint16 ρ (`32768` = 1,0), готово для Pix4D. | Только мультиспектральные камеры, и **только при привязке DAQ + калибровке камеры**; в противном случае пропускается. |
| `preview` / `display` | Полная цепочка предварительного просмотра в графическом интерфейсе (CCM + WB + гамма-коррекция в соответствии с профилем камеры). `lattice capture` присваивает имя `preview`; `array-capture`/`multi-capture` используют `display`. | Все камеры. |

Передайте один уровень, чтобы сохранить только его (`--processing debayered`). При запросе `all` уровни, не относящиеся к данному кулачку, пропускаются (и фиксируются в отчёте), но не вызывают ошибки — неподключённая или некалиброванная камера всё равно получает `raw` / `debayered` / `preview`.

Для любого кадра отраженного излучения фактически использованное значение нисходящего излучения DAQ записывается в сопутствующий файл **`.daq`** рядом с изображением (чтобы захват можно было переобработать позже) и указывается в строке `DAQ:`.

### Как выглядит папка с снимками

Каждый тип экспорта помещается в свою **собственную подпапку** в каталоге `-o`, поэтому в многоуровневом снимке типы никогда не смешиваются:

```
output/
├── raw/           capture_<ts>_SN<serial>_raw.tif
├── debayered/     capture_<ts>_SN<serial>_debayered.tif
├── radiance/      capture_<ts>_SN<serial>_radiance.tif
├── reflectance/   capture_<ts>_SN<serial>_reflectance.tif
├── preview/       capture_<ts>_SN<serial>_display.tif
├── index/         per-camera vegetation-index (LUT) render, when --index is on
├── composite/     array foreground/background live-view composite, when produced
└── *.daq          the downwelling reading matched to the capture
```

`<ts>` — это временная метка захвата, а `<serial>` — серийный номер камеры, поэтому одна синхронизированная группа имеет общую
временную метку для всех камер. **Обратите внимание на одно несоответствие:** уровень `display` хранится в папке
с именем `preview/`, тогда как сами файлы сохраняют `_display` в имени — папка и суффикс различаются
только для этого уровня. Неизвестные уровни попадают в папку с собственным именем, и если подпапку
не удается создать, файл записывается в корневую папку вывода, а не теряется.

**Повторная обработка папки с записями:**укажите `chloros-cli process` на**корневой каталог снимков**
(`output/`). `process` обычно импортирует только указанную вами папку, но если в ней нет
изображений и есть подпапки, он автоматически проходит по иерархии вниз — таким образом, корневыеподпапки корневого уровня и
корневой каталог `.daq` обрабатываются за один раз. Каждый уровень снимка импортируется как одно изображение, а
остальные уровни доступны в качестве режимов, а не как отдельные изображения для каждого уровня.

Прямое указание **подпапки уровня** (например, `output/raw/`) также работает. При этом корневая
папка `.daq` не учитывается, поэтому скопируйте или укажите данные сбора данных (DAQ) при повторном вычислении радиометрического
продукт из `raw/` — в противном случае не будет с чем сопоставить временную метку.

**Обработка всегда начинается с `raw`.** В рамках каждого захвата исходным источником конвейера является необработанный кадр;
`debayered`, `radiance`, `reflectance` и `preview` выступают в качестве режимов просмотра, но никогда не возвращаются
обратно в конвейер. Повторная обработка производного продукта привела бы к повторному применению виньетирования, CCM и
математические вычисления яркости, которые уже запечены в его пикселях, поэтому «Chloros» отказывается от этого, вместо того чтобы
проводить двойную обработку. Два последствия, о которых стоит знать:

- Рендеринги `index/` и `composite/` **никогда** не обрабатываются. Они являются выходными данными, а не захваченными изображениями —
  рендер с LUT «NDVI» не имеет значимой интерпретации яркости.
- Папка с кадрами, экспортированная **без** файла `raw` (например, `array-capture --processing reflectance`), не имеет
  легитимного источника для конвейера обработки. Эти захваты импортируются и отображаются нормально, но `process` пропускает
  их и сообщает об этом:

  ```
  [IMPORT-LEVEL] Skipping 4 already-processed file(s) with no raw source: capture_…_reflectance.tif
  [IMPORT-LEVEL] Processing starts from raw. Re-capture with --processing raw, or force an entry
                 point with --input-level.
  ```

  Если вам действительно нужно пропустить производный продукт — сессию концентратора, записанную с
  включённым флагом `demosaic`, или устаревшую папку — флаг `--input-level {raw,debayered,processed}` принудительно
  и отменяет пропуск. Этот флаг является специально предусмотренным «запасным выходом»; `auto` (по умолчанию)
  никогда не обрабатывает запись, не содержащую исходных данных.

### Пропущенные записи в массивах со смешанными фильтрами

При смешивании камер «RGB» и мультиспектральных камер в одном массиве `array-capture --processing radiance` (или `reflectance`) сохраняет мультиспектральные кадры и **пропускает** камеры «RGB» — яркость на пиксель по Байеру не имеет смысла для широкополосного датчика. CLI выводит на печать каждый сохраненный файл (с указанием уровня экспорта), каждый записанный файл `.daq` и каждый пропуск явно, поэтому количество файлов не вызывает удивления:

```
  Saved: output/sync_…_SN213800234.tif [reflectance] (SN:213800234, fid:1)
  Saved: output/sync_…_SN214000533.tif [reflectance] (SN:214000533, fid:1)
  Saved: output/sync_…_SN214701288.tif [reflectance] (SN:214701288, fid:1)
  DAQ:   output/sync_…_daq-e-54b5e0.daq
  Skipped: SN:214701292 (reflectance-not-applicable-to-rgb-cam filter=RGB)

  3 synchronized frames captured. (1 skipped)
```

Токены с причиной пропуска следуют шаблону `<level>-not-applicable-to-rgb-cam`. Отражательная способность также может быть пропущена с помощью `reflectance-skipped-no-fresh-dls` / `reflectance-skipped-bound-daq-unavailable (…)`, а также с помощью `dls-uncalibrated-band-<nm>`, если полоса в основном лежит за пределами радиометрически откалиброванного диапазона светового датчика DAQ (~374–974 нм) — среди поставляемых SKU только F988, для которого поддерживается рабочий процесс с использованием панели отражения.

Используйте `--processing debayered` (или `display`), чтобы включить каждую камеру независимо от типа фильтра, или значение по умолчанию `all`, чтобы за один раз получить все применимые уровни для каждой камеры.

## Режимы захвата, регистраторы и автономная переработка

Все они работают с **постоянным массивом** (сначала запустите `array-connect`). Они дублируют панель захвата в графическом интерфейсе.

### Режимы `array-capture`

`array-capture` — это единичная команда с четырьмя режимами затвора и набором переключателей экспорта:

| Режим | Флаг | Поведение |
| --- | --- | --- |
| **Одиночный** *(по умолчанию)* | (нет) | Одна синхронизированная группа захвата, затем выход. |
| **Непрерывный** | `--continuous` | Последовательные проходы до появления `Ctrl+C`, `--count N` или `--duration S`. |
| **Интервал** | `--interval S` | Один проход каждые `S` секунд (отсчитывается от начала каждого прохода), те же границы. |
| **Самый быстрый** | `--fastest` | Только необработанныеданные + назначенное значение сбора данных (DAQ) + композитный индекс; пропускает вычисления яркости/отражательной способности/отображения, чтобы кадр отображался быстро. Подразумевает `--processing raw --force-daq`. Переобработайте сохраненные данные `.daq` в откалиброванные продукты позже. |

Переключатели экспорта (комбинируются с любым режимом; все используют общий графический интерфейс и конечную точку SDK):

| Флаг | Эффект |
| --- | --- |
| `--processing LEVEL` | Один уровень экспорта или `all` (по умолчанию). |
| `--levels L1,L2,…` | Явное подмножество типов экспорта (например, `raw,radiance,reflectance`); **переопределяет `--processing`**. |
| `--aligned` / `--no-aligned` | Приводить несырой экспорт каждого элемента в соответствие с [профилем выравнивания](#alignment) (совместная регистрация). Необработанные данные остаются без выпрямления, но трансформация передаётся в метаданных. Если массив не имеет профиля, используется режим без выравнивания (с предупреждением). |
| `--index` / `--no-index` | Сохранять / пропускать наложение индекса растительности для каждой камеры, если оно настроено. По умолчанию: визуализировать его. |
| `--force-daq` | Сохранять назначенные показания DAQ/DLS в виде файла-сайдкара `.daq`, даже если ни один из выбранных уровней в этом не нуждается (например, при захвате только необработанных данных), чтобы кадры можно былов режиме офлайн в отражательную способность/индекс. |
| `--smart` | Дожидаться стабилизации AE на всех камерах перед запуском (см. [Smart-AE / Smart-Capture](#smart-ae--smart-capture)). |
| `--compression {deflate,none}` | Сжатие пикселей по методу «TIFF». `deflate` (по умолчанию) = zlib L1 без потерь + горизонтальный предиктор, ~4,1 МБ на кадр в полном разрешении; `none` = uncomсжатие, запись примерно в 5 раз быстрее при размере ~6,3 МБ на кадр — использовать для максимальной устойчивой скорости, если позволяет дисковое пространство. Оба варианта без потерь и при импорте читаются одинаково. |

> **Однократная запись TIFF + модель с устойчивой скоростью.**Снимки записываются за**один**проход tifffile, передающий пиксели + XMP + IFD0 «Производитель/Модель» (измерено на Mono12 в полном разрешении: 36 мс в сжатом виде / 6,5 мс в несжатом, по сравнению с ~148 мс для старого метода «запись, а затем перезапись с помощью ExifTool»); единственная оставшаяся работа ExifTool (доработка под-IFD EXIF) выполняется в асинхронном фоновом рабочем процессе, и кадр считается завершённым и готовым к импорту, даже если этот процесс так и не запустится. Обратите внимание, что сжатие DEFLATE удерживает GIL Python, поэтому сжатая запись**не**параллелизуется между потоками записи для каждой камеры — непрерывная съемка с 8 камерами в полном разрешении со скоростью датчика (~10,4 кадров/с) требует `--compression none`**и** диска класса NVMe (~500 МБ/с устойчивой скоростью записи). Тот же параметр доступен как `compression` на `POST /api/camera/array/capture`.

```bash
# Interval timelapse: one reflectance pass every 10 s for 5 minutes
chloros-cli lattice array-capture --interval 10 --duration 300 \
  --processing reflectance -o timelapse/

# Fastest grab for a moving rig — raw + .daq now, calibrate later
chloros-cli lattice array-capture --fastest -o flightline/

# Co-registered multi-band export (drop the index overlay)
chloros-cli lattice array-capture --processing reflectance --aligned --no-index -o out/
```

### `array-record` — видео/GIF с комбинированным индексом (для мониторинга)

Записывает всё, что отображается в **режиме просмотра с комбинированным индексом в реальном времени**, в файл `.avi` (и, опционально, в файл `.gif`). Поскольку он подключается к композитному потоку в реальном времени, комбинированный поток должен быть открыт (например, массив просматривается в графическом интерфейсе), чтобы кадры поступали. Он проверяет ход записи каждые 2 с и останавливается при появлении файлов `--duration`, `Ctrl+C` или при самопроизвольном завершении работы рекордера.

```bash
# 30-second combined-index clip at 10 fps, plus a GIF
chloros-cli lattice array-record --duration 30 --fps 10 --gif -o monitoring/
```

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `--array-id ID` | только массив | Целевой массив (пропустить, если подключен только один). |
| `-o, --output DIR` | `output` | Каталог вывода (локальный для бэкэнда). |
| `--fps F` | `10` | Частота кадров записи. |
| `--duration S` | до Ctrl+C | Автоматическаяостановка через `S` секунд. |
| `--gif` | выкл. | Также записывать анимированный GIF. |
| `--gif-only` | выкл. | Записывать только GIF (без `.avi`). |

### `array-burst` — серия снимков в формате raw-Bayer с высокой частотой кадров (для анализа)

Считывает буфер синхронизированной группы цикла захвата напрямую — **не требуется цепочка калибровки, exiftool или просмотр в реальном времени** — поэтому работает на полной скорости съёмки камеры. Записывает кадры в формате RAW + манифест для каждого кадра + один файл `.daq` на каждое отдельное считывание DLS в рамках `<output>/bursts/<base>/`. Переработайте в автономном режиме (следующая команда) или передайте `--build`, чтобы сделать это сразу после остановки.

```bash
# 5-second raw burst, then build the combined index video in one shot
chloros-cli lattice array-burst --duration 5 --build \
  --products combined:index --fps 10 -o capture/
```

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `--array-id ID` | только массив | Целевой массив. |
| `-o, --output DIR` | `output` | Каталог вывода (пакеты попадают в `<DIR>/bursts/<base>/`). |
| `--duration S` | до Ctrl+C | Автоматическая остановка через `S` секунд. |
| `--max-frames N` | без ограничений | Автоматическая остановка после `N` необработанных кадров. |
| `--build` | выкл. | После остановки немедленно переобрабатывать пакет (так же, как `array-build-video`). |
| `--products …` | `combined:index` | С `--build`: какие видео создать (см. ниже). |
| `--fps F` | `10` | С параметром `--build`: частота кадров выходного видео. |
| `--save-tiffs` | выкл. | С параметром `--build`: также сохранять откалиброванные TIFF-файлы для каждого кадра. |
| `--gif` | выкл. | С параметром `--build`: также записывать анимированные GIF-файлы. |

### `array-build-video` — автономная переработка сохраненной серии снимков

Сопоставляет каждый необработанный кадр по времени с ближайшим сохраненным значением `.daq` и пропускает его через **ту же цепочку интенсивности излучения / отражательной способности / индексной цепочке, что и конвейер импорта**, в результате чего создается одно или несколько видео.

`--products` представляет собой список элементов `kind:level`, разделенных запятыми, где `kind` ∈ `per_cam` | `combined`, а `level` ∈ `radiance` | `reflectance` | `index`. Для простого `level` (без `kind:`) по умолчанию используется `per_cam`. По умолчанию используется `combined:index`.

```bash
# Per-cam reflectance video for every member + one combined NDVI video
chloros-cli lattice array-build-video \
  --burst-dir "capture/bursts/2026-06-24_141500" \
  --products per_cam:reflectance,combined:index \
  --fps 10 --save-tiffs
```

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `--burst-dir DIR` | (обязательно) | Путь к папке с пакетами данных (`…/bursts/<base>/`). |
| `--products …` | `combined:index` | Список `kind:level`, как указано выше. |
| `--fps F` | `10` | Частота кадров выходного видео. |
| `--save-tiffs` | выкл. | Также сохранять откалиброванные TIFF-файлы для каждого кадра вместе с видео. |
| `--gif` | выкл. | Также записывать анимированные GIF-файлы. |

> **Выберите подходящий рекордер.** `array-record` — *уровень мониторинга* — он захватывает композитный сигнал в реальном времени в том виде, в котором он отображается, и требует открытого потока. `array-burst` → `array-build-video` — *уровень анализа** — сохраняет необработанные данные с датчика с полной скоростью и впоследствии реконструирует откалиброванные видеоролики яркости/отражения/индекса, при этом не требуется просмотр в реальном времени.

### Одноканальные (M3M) однодиапазонные камеры

Линейка **M3M**является монохромным аналогом модели Bayer**M3C**: одна узкополосная интерференционная фильтрация на камеру (`M3M-<lens>-F<wavelength>`, например, `M3M-L87-F685`), поэтому датчик обеспечивает**один диапазон оттенков серого** без мозаики Байера. Здесь не нужно проводить демозаику, устранять межканальные помехи и настраивать баланс белого — весь процесс цветопередачи «RGB» просто не применяется.

Что это означает для камеры CLI:

- **`lattice white-balance`, `lattice color-profile`, `lattice color`**обнаруживают монохромную камеру и**пропускают её с однострочным сообщением** вместо того, чтобы применять бессмысленные настройки. При этом они по-прежнему нормально работают с камерой RGB /Bayer M3C в той же сессии.
- **`lattice calibrate` / `process --reflectance` / `array-capture --processing radiance`** по-прежнему работают — радиантность и отражательная способность представляют собой радиометрические карты *по каждому диапазону* и прекрасно определены для одного диапазона. Монохромные кадры имеют **идентичную** матрицу отклика датчика (без 3×3-разложения), поэтому плоскость проходит через математику калибровки без изменений.
- **Одна монохромная камера не может вычислить индекс растительности.**NDVI / NDRE /и т. д. требуют как минимум двух полос (например, Red + NIR). Чтобы получить индекс с помощью монохроматического оборудования, направьте**несколько** камер M3M на разные длины волн, объедините их в один многополосный стек и рассчитайте индекс *именно для него*:

```bash
# Red (660) + NIR (850) mono pair -> aligned 2-band stack -> NDVI
chloros-cli lattice array-connect --serials SN_RED,SN_NIR
chloros-cli lattice index --live --profile align.json \
  --preset NDVI --channel red=Red_660 --channel nir=NIR_850 \
  --save-multiband -o output/
```

`--channel` — символы должны **точно** (учитывается регистр; NDVI — строчные `red`,`nir` — см. `--list-presets`), а название диапазона указывает на диапазон в выровненном стеке (автономный режим также допускает индексы диапазонов с нулевым началом, напримернапример, `--channel red=0 --channel nir=1`).

Дискриминатором во всём стеке является токен `M3M` в строке модели (он никогда не появляется в строке `M3C`), отображаемый в графическом интерфейсе пользователя/SDK как `is_mono`.

## Настройка и оптимизация сетевой карты хоста (массивы LATTICE)

Камеры LATTICE передают поток GVSP через Ethernet-адаптер хоста, поэтому для массивов с несколькими камерами **драйвер**адаптера и**размер кольца приёма** имеют такое же значение, как и скорость соединения. Неправильные настройки отображаются в виде ошибок `FRAMES WILL DROP` / `Reduce ROI to enable` на панели «Настройки массива» (а также в `lattice network-analysis` / `analyze_array_network()` в «SDK»), даже если сами камеры находятся в исправном состоянии.

### USB-адаптеры 10 Гбит/с — Realtek RTL8157 («Контроллер семейства Realtek USB 10GbE»)

| Элемент | Требуемое значение | Почему это важно |
| --- | --- | --- |
| **Версия драйвера**|**≥ v10.67 (январь 2026 г.)**, INF `rtump64x64sta.inf` | Устаревший драйвер**2016**драйвер (v10.65, `rtump64x64.inf`) некорректно обрабатывает переход в режим сна и вызывает ошибки с кодом**`DRIVER_POWER_STATE_FAILURE` (синий экран `0x9F`)**при выключении/перезапуске/переходе в спящий режим. Переход зависает (таймаут ~5 минут), пользователь вынужден принудительно выключить систему, а повторяющиеся некорректные выключения**приводят к повреждению репозитория WMI**(PowerShell и другие инструменты начинают выдавать ошибки с кодом `Invalid class`) и**зависает стек USB** при следующей загрузке (сетевая карта не включается; USB-накопители перестают распознаваться). Обновите драйвер с сайта realtek.com (или у производителя USB-ключа), прежде чем полагаться на корректные перезапуски. |
| **Буферы приёма**— ключевое слово `ReceiveBufferLen` |**256**(максимальное значение драйвера) | Кольцо приёма сетевой карты. Значение по умолчанию драйвера**32**оставляет только ~0,26 МБ доступного кольца — это слишком мало для серии снимков с нескольких камер — поэтому панель массива выдает сообщение `Sim-emit burst … exceeds NIC RX ring usable capacity 0.26 MB` и блокирует подключение. При значении**256**кольцо становится достаточно большим (**~13,5 МБ, измеренное на лабораторном хосте с интерфейсом 10GbE**), что обеспечивает конвейеру приёма реальный запас пропускной способности для пакетных передач GVSP с несколькими камерами. (Решение о том, *соединяется* ли данная конфигурация, принимается на основе двух проверок — проверки допуска с учётом **опустошения**и проверки**совокупной переподписки** — а не на основе простого сравнения объёма пакета с объёмом кольца; см. [Модель fps и пакетов массива](#array-fps--burst-model).) |
| **URB приёма**— ключевое слово `PendingReceives` |**64** (макс.) | Блоки запросов USB в процессе передачи; увеличиваются одновременно с буферами приёма для поглощения пакетных потоков. |
| **Jumbo Frame** — ключевое слово `*JumboPacket` | **9014** | Требуется для пакетов GVSP размером 9000 байт (в 6 раз меньше пакетов накадра, чем 1500). |

> ⚠️ **Обновление драйвера сетевой карты СБРОСИТ эти расширенные свойства до значений по умолчанию.**После обновления или замены драйвера адаптера**повторно примените** настройки `ReceiveBufferLen=256` и `PendingReceives=64`, иначе панель массива снова начнёт сбрасывать данные, даже если «в аппаратном обеспечении ничего не изменилось». Это основная причина того, что ранее работавшая установка внезапно отказывается подключаться.

Применяйте из **PowerShell с правами администратора** (замените на название вашего адаптера, например, `"Ethernet 5"`):

```powershell
Set-NetAdapterAdvancedProperty -Name "Ethernet 5" -RegistryKeyword ReceiveBufferLen -RegistryValue 256
Set-NetAdapterAdvancedProperty -Name "Ethernet 5" -RegistryKeyword PendingReceives  -RegistryValue 64
Get-NetAdapterAdvancedProperty  -Name "Ethernet 5" -RegistryKeyword ReceiveBufferLen,PendingReceives   # verify
```

> **`lattice network --fix` охватывает адаптеры USB 10GbE.** Теперь система определяет тип адаптера и настраивает правильное ключевое слово receive-ring: `*ReceiveBuffers`→2048 для сетевых карт PCIe (Intel I219 и т. д.), либо `ReceiveBufferLen`→256 + `PendingReceives`→64 для контроллера Realtek **USB** 10GbE (который не предоставляет параметр `*ReceiveBuffers`). Целевые значения ограничиваются максимальным значением, сообщаемым каждым драйвером (`NumericParameterMaxValue`), поэтому никогда не записывается значение, выходящее за пределы диапазона. Запускайте его из терминала с **повышенными** правами; как и при любой настройке на основе реестранастройка на основе реестра, изменение вступает в силу после перезапуска адаптера или перезагрузки системы. Приведённые выше ручные команды `Set-NetAdapterAdvancedProperty` остаются хорошей альтернативой — они применяются в режиме реального времени (повторная привязка адаптера) без перезапуска.

### Основы сети (все соединения LATTICE)

- **Адресация:** локальный для канала `169.254.0.0/16` (GigE Vision LLA). Хост получает статический адрес `169.254.x.x/16`; камеры + DAQ-E самостоятельно назначают адреса в том же диапазоне. DHCP и шлюз не требуются.
- **Размер пакета:**предпочтительно jumbo (9000), но пусть автопроверка определит его — она повторно измеряет размер при каждом подключении и уже учитывает ограничение камеры на 1500байтовое ограничение ICMP с помощью GVSP-пробы, поэтому он переходит на jumbo везде, где кабель действительно его поддерживает. Задавайте значение с помощью `CHLOROS_GVSP_PACKET_SIZE_FORCE=9000` только тогда, когда вы знаете лучше, чем проба, и отдавайте предпочтение настройке для каждой команды, а не постоянной: фиксированное значение обходит пробу, поэтому, если канал на самом деле не может передавать 9000,**каждый** захват завершится тайм-аутом с `SC_ERR_TIMEOUT -1011` (см. [Переменные среды](#environment-variables)).
- **Кольцо RX масштабируется с `ReceiveBufferLen`:**при значении по умолчанию `32` доступный объем кольца составляет ~0,26 МБ (слишком мало для любого многокамерного пакета); при максимальном значении `256` он большой (~13,5 МБ, измерено на лабораторном хосте с 10GbE), что обеспечивает реальный запас пропускной способности. Решение о том, будет ли конфигурация подключена, принимается на основе проверки допустимости с учётом нагрузки**и** проверки совокупной переподписки, описанной ниже, — а не на основе простого сравнения скорости серийной передачи данных и пропускной способности кольца.

### Модель частоты кадров массива и пакетной передачи

Как читать панель настроек массива (и `lattice analyze-array` / `analyze_array_network` на «SDK»):

- **Данные в режиме «Burst» суммируются для каждой камеры в реальном пиксельном формате этой камеры.**Монохромные камеры**M3M**передают поток**Mono12 (2 бита на пиксель)**; камеры**M3C**с матрицей Байера передают 8- или 12-битный поток (TRI032S незаметно выдает BayerRG12, даже если запрашивается BayerRG8). Таким образом, кадр с полным разрешением от 4 камер составляет**~12,6 МБ, если все 8-битные, но ~25 МБ при использовании трёх 12-битных монохромных камер**. Проекция определяет формат каждой камеры по её модели (кеш идентификаторов), поэтому пакет данных соответствует тому, что фактически передаётся по каналу — а не исходит из универсального допущения о формате BayerRG8.
- **Скорость USB-адаптера Ethernet ограничена 200 МБ/с, независимо от заявленных характеристик.** Таблица эффективности, которая преобразует скорость канала в показатель устойчивой пропускной способности, основана на данных PCIe; USB-сетевая карта объявляет свою скорость *Ethernet*, но ограничена возможностями шины USB и её драйвера. USB-адаптер 10GbE, использовавшийся для достижения «устойчивой» скорости ~1063 МБ/с — показателя, который никогда не проверялся — привёл к тому, что из-за неравномерной передачи данных было повреждено 6–18 % кадров, хотя при этом по-прежнему отображалась нормальная целевая частота кадров. Скорость сетевых адаптеров, подключаемых по USB, теперь ограничена **200 МБ/с** в абсолютном выражении (ограничением является шина, поэтому скорость не зависит от номинальных характеристик; USB-адаптер 1 Гбит/с обеспечивает скорость ~80 МБ/с и не подвержен этому ограничению). `wire_ceiling_source` в записи о возможностях указывает на это словами, а `nic_is_usb` помечает это. Переопределить любое из этих значений можно с помощью `--wire-ceiling-mbps`.
- **Допуск учитывает нагрузку на канал, а не весьпакетный режим по сравнению с кольцевым.** Одновременный пакетный поток должен умещаться только в *переходный бэклог* = `max(0, Σ per-cam arrival − host drain) × emit_window`, а не во весь поток целиком. В структуре с быстрым хостом и медленными камерами (например, **PCIe**хост 10G + 4 камеры по 1 Гбит/с: поступление ≈ 320 МБ/с, сброс ≈ 1063 МБ/с) хост сбрасывает данные быстрее, чем камеры их наполняют, накопитель ≈ 0, поэтому симуляция полного разрешения**пропускает**, несмотря на то, что пакетный поток объёмом 25 МБ превышает размер кольца 13,5 МБ. Подключите те же четыре камеры к**USB**-адаптеру 10 Гб/с, и скорость сброса составит 200 МБ/с, а не 1063 — поток данных превышает скорость слива, и потери проявляются в виде повреждённых кадров, а не в виде снижения частоты кадров. На хосте 1 ГбE нижний порог DLThr камер (31,25 МБ/с) приводит к тому, что поток данных превышает скорость слива → он корректно**блокирует** (для *этого* класса блокировок; чтобы избежать этого, уменьшите область интереса (ROI) или используйте биннинг ≥ 2). Допуск осуществляется одним из **двух** контрольных механизмов — другим является приведённая ниже проверка на превышение подписки на агрегированном уровне.
- **Прогнозируемое количество кадров в секунду (fps) представляет собой консервативный верхний предел для последовательного извлечения.**Цикл захвата хоста в настоящее время извлекает буфер каждой камеры**последовательно**(примерно по одному окну передачи на камеру), поэтому цикл ограничен `max(readout+emit, N × emit)`, при этом вывод данных с каждой камеры ограничивается**каналом доступа**камеры (1 GbE ≈ 80 МБ/с), а не восходящим каналом хоста. Для 4-камерного полногомассива с 12-битным разрешением,**~2,8 кадров в секунду**, что соответствует измеренным ~2,7–3,0. fps намеренно**не зависит от экспозиции**, поэтому в слабо освещённых сценах фактическая частота может немного опускаться ниже верхнего предела по мере увеличения экспозиции. По-настоящему ограничивает частоту кадров последовательный вывод данных; его параллелизация повысила бы верхний предел до скорости одиночной передачи.
- **Совокупная переподписка является жестким препятствием для установления соединения.**Минимальное выделение пропускной способности на каждую камеру составляет**8 МБ/с**(`ARRAY_PER_CAM_FLOOR_BPS`), поэтому как только минимальное значение фиксируется, совокупный спрос (`per_cam × N`) может превысить**безопасный для предотвращения коллизий предел канала**(`sustained × sim_emit_factor`). Практические пределы при полном разрешении на 1 Гбит/с:**6 камер при 1500 MTU, 9 с джамбо-кадрами**. Этот предел зависит исключительно от канала и нижнего порога — он**не зависит от размера кадра**, поэтому**объединение в бины и уменьшение области интереса (ROI) НЕ помогают** (они снижают количество байтов на *кадр*, а не количество байтов в *секунду*, определяемое GevSCPD); единственные способы решения — уменьшение количества камер, использование джамбо-фреймов на всем протяжении канала или более быстрый сетевой адаптер. Симптомом будет потеря пакетов GVSP, а не плавное снижение частоты кадров, поэтому `analyze-array` обнуляет показатели достижимой частоты кадров и выводит `**OVER-SUBSCRIBED**`, а `array-connect` с зафиксированным разрешением **отказывается устанавливать соединение** (в противном случае алгоритм walk-down группирует кадры, что также не устраняет этот класс блокировок). `CHLOROS_ARRAY_ALLOW_OVERSUBSCRIBED=1` понижает уровень отказа до громкого предупреждения для тестовой работы — см. [Переменные среды](#environment-variables).

### Состояние массива — какая подсистема теряет кадры

`GET /api/camera/array/<array_id>/capability` подключенного массива содержит активный
блок `health`, переоцениваемый в скользящем **10-секундном** окне. Он разбивает потери кадров
на две причины, требующие противоположных мер устранения, вместо того, чтобы сообщать об одной «неполной»
частоте, не указывающей ни одну из них:

| Поле | Что это означает | Какая подсистема |
| --- | --- | --- |
| `gvsp_corrupt_rate_pct` (по серийному номеру) | Кадр **прибыл, но имел структурные ошибки**— потеря пакетов GVSP. |**Сеть**: пропускная способность кабеля, темп передачи, кольцо приёма сетевой карты, MTU |
| `never_arrived_rate_pct` (по серийному номеру) | Кадр **вообще не поступил**— камера не сработала или данные не были отправлены. |**Триггер / синхронизация**: кабель M8, `--line`, `TriggerMode` |
| `worst_gvsp_corrupt_pct` / `worst_never_arrived_pct` | Наихудшая скорость передачи данных камерыпо каждой из них. | — |
| `per_cam_rate_pct` | Совокупный показатель неполной синхронизации на каждую камеру (обе причины вместе). | — |
| `stable_for_seconds` | Как долго каждая камера оставалась на уровне ниже 0,01 %. | — |

При значении выше 5 % бэкенд записывает строку `[array-health <id>] WARN` с указанием причины — при
первом нарушении, при смене диапазона серьезности, раз в минуту, пока проблема сохраняется, и один раз, когда
она устраняется. Повреждённая половина записывает `[gvsp-corrupt <SN>]` при первом срабатывании для каждой камеры и
причине, затем сводные данные каждые 60 с. Каждая оценка по-прежнему попадает в файл журнала бэкэнда;
счётчики увеличиваются при каждом буфере, независимо от того, что выводится.

В той же записи указывается номер, с которым связано всё выделение:

| Поле | Что означает |
| --- | --- |
| `wire_ceiling_mbps` | Действующий бюджет пропускной способности хоста, МБ/с. |
| `wire_ceiling_source` | Откуда взято это число, в виде текста — например, `USB-capped 200 MB/s (was theoretical 1062; PnPDeviceID=USB\VID_0BDA&PID_815A)` или `user override 120 MB/s (auto said 200)`. |
| `wire_ceiling_is_user_set` | `true`, когда `--wire-ceiling-mbps` (или поле **Бюджет пропускной способности** ) задает его. |
| `nic_is_usb` | `true` для USB-адаптера Ethernet — см. ограничение в 200 МБ/с выше. |

**Интерпретация:** ненулевое значение `gvsp_corrupt_rate_pct` при значении `never_arrived_rate_pct`, равном 0,
означает, что запуск и синхронизация кабеля идеальны, а 100 % потерь приходятся на сетевой
путь — уменьшите значение `--wire-ceiling-mbps` и повторно подключитесь. Обратная картина указывает на
кабель синхронизации или линию запуска.

> **`--target-fps` не является показателем поврежденных фреймов.** Темп GevSCPD задается
> однократно при подключении, поэтому снижение частоты триггера изменяет коэффициент заполнения, а не
> скорость одновременной передачи пакетов. Замеренное 5-кратное снижение нагрузки не дало улучшения;
> снижение максимальной скорости кабеля с 240 до 200 МБ/с привело к снижению доли повреждённых данных на той же установке с 10,4 %
> до 0,00 %.

> **Автоматическое сжатие в середине потока недоступно в прошивке TRI032S.** Работающий массив
> не может исправить это самостоятельно; отсоединитесь и подключитесь заново, чтобы механизм выбора времени подключения мог
> перепланировать работу с учётом нового предельного значения.

### Симптом → устранение

| --- | --- | --- |

| Камеры отсутствуют в опубликованных группах; `health.never_arrived_rate_pct` отличен от нуля, `gvsp_corrupt_rate_pct` 0 | Тракт триггера/синхронизации — камеры не срабатывают, проблема не в сети | Проверьте синхронизационный кабель M8 и `--line`; убедитесь, что все устройства включены (`TriggerMode=On`) |
| Превышение значений `**OVER-SUBSCRIBED**` / `Wire budget` в `analyze-array` или отказ в подключении с зафиксированным разрешением (`array over-subscribes the wire`) | Совокупный спрос на каждую камеру (минимум 8 МБ/с × N камер) превышает безопасный для коллизий предел канала — 6 камер в полном разрешении по 1 Гбит/с при 1500 МТУ, 9 с джамбо-кадрами | Меньшее количество камер,кадров «джамбо» по всей цепочке или более быстрый сетевой адаптер. **ROI/биннинг НЕ помогут** (предел не зависит от размера кадра). `CHLOROS_ARRAY_ALLOW_OVERSUBSCRIBED=1` переопределяется на тестовом стенде (допускает потерю пакетов) |

## `chloros-cli daq`

Команды спектрального датчика. Два класса:
- **`pool-*`**— «тонкие» клиенты HTTP, которые управляют датчиком через постоянный пул бэкэнда.**Это поддерживаемый путь и единственный, присутствующий в поставляемом CLI.** Бэкенд владеет каналом передачи данных, поэтому графический интерфейс, а также скрипты CLI и SDK используют один активный дескриптор, вместо того чтобы конкурировать за доступ к последовательному порту.
- **Все остальное**(`test`, `record`, `live`, `stream`, `connect`, `info`, `net`, `ota`, `sample-rate`, `calibrate`, `serve`, `ws`, `udp`, `mqtt`, `reflectance`, `login`, `logout`, `status`) — прямой доступ к аппаратному обеспечению, описанный ниже для полноты информации. Для них требуется пакет `daq` Python, который**не входит ни в один из поставляемых артефактов**: скомпилированный файл CLI его не содержит (`scripts/Build-CLI.ps1` устанавливает `--nofollow-import-to=daq`, а транспорты `pyserial` / `bleak` / `zeroconf` вместе с ним), и пакет PyPI SDK также не содержит его. Они работают только из исходного кода, поэтому рассматривайте их как MAPIR — внутренний путь разработки, а не как что-то, к чему стоит стремиться.
- **`discover` / `list`** находятся посередине: они являются прямыми-аппаратные команды из исходного кода, но в готовой сборке они переключаются на `pool-discover`, и сканирование выполняется бэкэндом. Таким образом, сканирование работает везде — и это важно, поскольку это единственный способ узнать MAC-адрес BLE устройства DAQ-M.

> **`chloros-cli daq --help`** (а также `-h` / `help`) перечисляет подкоманды `pool-*` — справка намеренно направляется в пул клиента пула, чтобы она отражала команды, которые действительно выполняются. Если вы вызовете прямуюподкомманду, связанную с аппаратным обеспечением, в поставляемой сборке, она завершится с явной ошибкой, в которой будет указан отсутствующий пакет и дана ссылка на `pool-*`; ничего не завершается без уведомления. (`discover` / `list` — это исключения — они перенаправляют на `pool-discover` и просто работают.)
>
> **Все, что нужно клиенту, доступно через `pool-*`** — подключение, потоковая передача, запись откалиброванных файлов `.daq` и замена профилей конденсаторов. Устройство сбора данных (DAQ) также можно управлять из Python с помощью `chloros_sdk.connect_daq_sensor()`, который использует тот же общий путь.

### Рабочий процесс первого подключения датчика DAQ

```bash
# 1. Smart-detect any DAQ on this machine (Ethernet → BLE → USB precedence)
chloros-cli daq connect

# 2. Detailed scan: every transport, showing the address to connect with.
#    This is how you find a DAQ-M's BLE MAC — unlike a DAQ-E hostname or a
#    DAQ-U COM port, a MAC isn't printed on the device or listed by the OS.
chloros-cli daq discover                      # or: daq pool-discover
chloros-cli daq discover --only ble           # BLE only
chloros-cli daq discover --json               # machine-readable

# 3. Open a persistent pool session (handle stays alive across CLI calls)
chloros-cli daq pool-connect           # smart-detect
chloros-cli daq pool-connect --port COM3                       # DAQ-U on a specific COM port
chloros-cli daq pool-connect --mac AA:BB:CC:DD:EE:FF           # DAQ-M by BLE MAC
chloros-cli daq pool-connect --eth-host daq-e-xxx.local        # DAQ-E by hostname

# 4. List what's in the pool, including the sensor_id you'll use next
#    (DAQ-U ids look like 'CB-7C-A8-2E-5F'; DAQ-E ids like 'daq-e-def330')
chloros-cli daq pool-list

# 5. Read the latest spectrum frame
chloros-cli daq pool-latest --sensor-id CB-7C-A8-2E-5F

# 6. Record a calibrated .daq file for 60s
chloros-cli daq pool-record --sensor-id CB-7C-A8-2E-5F --duration 60 \
  -o ~/Documents/spectra --device-name "field-A"

# 7. Release
chloros-cli daq pool-disconnect --sensor-id CB-7C-A8-2E-5F
```

### Справочник `pool-*`

| Подкоманда | Назначение |
| --- | --- |
| `daq pool-connect` (smart-detect) | Открыть датчик в пуле бэкэнда. |
| `daq pool-connect --port PORT` | DAQ-U на определённом последовательном порте. |
| `daq pool-connect --ble` | DAQ-M через BLE, автоматическое-сканирование. |
| `daq pool-connect --mac MAC` | DAQ-M по BLE на известный MAC (подразумевает `--ble`). |
| `daq pool-connect --eth-host HOST` | DAQ-E по Ethernet на известном хосте. |
| `daq pool-connect --eth` | DAQ-E по Ethernet, хост обнаружен автоматически (mDNS + резервный ARP; работает с пустым кэшем ARP на Windows и Linux). |
| `daq pool-connect --integration-time MS --frame-avg N --no-ae` | Настройка окна интеграции / состояния AE. |
| `daq pool-connect --no-stream` | Установить соединение, но пока не начинать потоковую передачу (возобновление с помощью `pool-stream --start`). |
| `daq pool-connect --cap-id {none, fov_15, fov_30, fov_45, fov_60, fov_90, sunshine_cosine}` | Профиль коррекции Cap. По умолчанию на бэкенде используется `sunshine_cosine`. |
| `daq pool-discover [--only usb,ble,eth] [--timeout SEC] [--json]` | Просканировать каждый транспорт на наличие датчиков, к которым можно подключиться, не устанавливая соединения. **Так можно найти MAC-адрес BLE устройства DAQ-M.** В поставляемых сборках команды `daq discover` / `daq list` автоматически перенаправляются сюда. Датчики, уже открытые в пуле, не отображаются — подключённый DAQ-M перестаёт передавать рекламу — поэтому для них используйте `pool-list`. |
| `daq pool-list` | Показать все датчики в пуле бэкенда. |
| `daq pool-disconnect --sensor-id ID [--all]` | Освободить. |
| `daq pool-latest --sensor-id ID [--recent N] [--json]` | Последние N кадров спектра. |
| `daq pool-stream --sensor-id ID [--start \| --stop]` | Возобновление / приостановка потоковой передачи. |
| `daq pool-record --sensor-id ID [--duration SEC] [--output DIR] [--device-name NAME] [--stop]` | Запуск / остановка записи в формате .daq. |
| `daq pool-set-cap --sensor-id ID --cap-id CAP` | Смена профиля коррекции емкости во время выполнения. |

### Подкоманды прямого доступа к аппаратному обеспечению (только при извлечении исходного кода — отсутствуют в поставляемых сборках)

> Приведены для полноты картины. Для их работы требуется пакет `daq` Python, а также `pyserial` / `bleak` / `zeroconf`, ни один из которых не входит в состав скомпилированной версии CLI или репозитория PyPI SDK — они запускаются только из исходного кода, полученного с MAPIR. **Если вы используете выпущенную сборку Chloros, используйте вместо этого приведенные выше команды `pool-*`**; они охватывают подключение, потоковую передачу, запись и выбор кап.

```bash
chloros-cli daq test --port COM3                           # Verify connection
chloros-cli daq connect --eth                              # Smart-detect over ETH
chloros-cli daq info --eth-host daq-e-xxx.local            # Device summary as JSON
chloros-cli daq discover --only usb,ble --timeout 5        # Scan local interfaces
chloros-cli daq list                                       # Alias of discover
# ^ discover/list are the exception in this section: in a shipped build they
#   fall back to `pool-discover` (the backend does the scan), so they work
#   without a source checkout. The only difference is that the fallback needs
#   the Chloros backend running, as all pool-* commands do.

# Streaming JSON Lines to stdout (pipeable)
chloros-cli daq stream --port COM3 --format jsonl --photometrics

# Record to .daq for 60 seconds
chloros-cli daq record --port COM3 --duration 60 -o ~/Documents/spectra/

# Live spectrum visualization in a window
chloros-cli daq live --port COM3 --record

# Dual-sensor reflectance (ambient + object) → JSON Lines
chloros-cli daq reflectance \
  --ambient-eth-host daq-e-field.local \
  --object-eth-host daq-e-canopy.local \
  --record -o ~/Documents/reflectance/

# Convenience: pick integration_time + frame_avg for a target rate
chloros-cli daq sample-rate --port COM3 --target-hz 5

# Calibration profile management
chloros-cli daq calibrate --port COM3 --list
chloros-cli daq calibrate --port COM3 --set field_calibration_2026_05

# DAQ-E network config (mDNS auto-discovers the host)
chloros-cli daq net --eth-host daq-e-xxx.local set-ip --mode static --ip 192.168.2.20
chloros-cli daq net --eth-host daq-e-xxx.local set-name "sky-sensor"
chloros-cli daq net --eth-host daq-e-xxx.local set-ptp --enabled true --domain 0
chloros-cli daq net --eth-host daq-e-xxx.local set-auto-stream true          # auto-stream on boot
chloros-cli daq net --eth-host daq-e-xxx.local set-require-signature         # require factory-signed cal (fw v1.6.0+; refused while the held cal is unsigned)
chloros-cli daq net --eth-host daq-e-xxx.local set-time                      # push host clock (refused when PTP SLAVE)
chloros-cli daq net --eth-host daq-e-xxx.local set-auth-token --current "" --new "s3cret"   # control-channel auth ("" new = disable)
chloros-cli daq net --eth-host daq-e-xxx.local set-ota-password "newpass"    # change OTA password (min 4 chars)
chloros-cli daq net --eth-host daq-e-xxx.local factory-reset                 # clear all NVS settings and reboot
chloros-cli daq net --eth-host daq-e-xxx.local reboot

# OTA firmware update
chloros-cli daq ota --eth-host daq-e-xxx.local \
  --firmware daq_e_1.21.bin --password mapir-daq-e

# Bridge spectra to other protocols
chloros-cli daq serve --port COM3 --tcp-port 9000           # TCP JSON-lines
chloros-cli daq ws    --port COM3 --ws-port 9001            # WebSocket
chloros-cli daq udp   --port COM3 --udp-port 9002           # UDP broadcast
chloros-cli daq mqtt  --port COM3 --broker mqtt.example.com --topic daq/spectrum
```

## `chloros-cli project`

Открытие, подключение и управление сохраненным проектом Chloros (папка, содержащая файлы `cameras.json` + `sensors.json` + `project.json`). Все операции проходят через бэкэнд, поэтому графический интерфейс и файл CLI отражают одинаковое состояние оборудования.

### Справочник подкоманд

| Подкоманда | Назначение |
| --- | --- |
| `project open PATH` | Вывести манифест устройств проекта (камеры, массивы, датчики). |
| `project devices PATH [--reconnect]` | Вывести список или повторить обнаружение. |
| `project connect PATH [--cameras-only] [--sensors-only]` | Подключить все сохраненные камеры / массивы / датчик. |
| `project capture PATH NAME [-o DIR] [--format FMT] [--exposure US] [--gain DB] [--prefix P]` | Однократная съемка с указанной камеры или массива. |
| `project burst PATH NAME [-n N] [-i S] [-o DIR] [--format FMT] [--exposure US] [--gain DB] [--prefix P]` | Серия из N кадров с указанной камеры или массива (по умолчанию 5; `-i/--interval` — интервал между кадрами в секундах, по умолчанию 0). Серии снимков из массива удаляют дубликаты повторяющихся синхронизированных групп (контроль устаревания), чтобы массив с частичным циклом не мог вернуть N копий одного кадра; выводит результаты по каждой итерации. |
| `project stream PATH NAME [-n N] [--fps F] [-o DIR] [--format FMT] [--exposure US] [--gain DB] [--poll-interval S]` | Передача потока на диск посредством задания бэкэнда. `--poll-interval` = интервал в секундах между опросами `/stats` (по умолчанию 2,0). |
| `project sensor read PATH NAME [--json]` | Последний кадр спектра. |
| `project sensor log PATH NAME --seconds SEC [-o DIR] [--device-name NAME]` | Запись .daq. |
| `project run PATH RECIPE.yaml` | Выполнение рецепта захвата YAML/JSON. `--dry-run` проверяет правильность без запуска. |
| `project align calibrate PATH NAME [--method M] [--model M] [--frames N] [--reference SN] [--max-features N] [--ratio-threshold F] [--ransac-threshold-px F] [--min-matches N] [--max-reproj-err-px F] [--checkerboard RxC] [--name PROFILE]` | Вычислить выравнивание для массива — см. [таблицу флагов ниже](#project-align-calibrate-options). |
| `project align status PATH NAME [--json]` | Вывести текущий профиль выравнивания. |
| `project align clear PATH NAME` | Удалить кэшированный профиль. |
| `project align tweak PATH NAME --serial SN --dx N --dy N --rotation-deg N --scale N` | Сместить преобразование одного подчиненного узла. |
| `project align export PATH NAME --to FILE` | Сохранить профиль в файле JSON. |
| `project align import PATH NAME --from FILE [--no-validate]` | Загрузить сохраненный профиль. |

#### Параметры `project align calibrate`

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `--method {feature_orb, feature_akaze, phase_correlation, checkerboard, manual}` | `feature_orb` | Метод выравнивания. **Эти названия отличаются от `lattice align-calibrate`**, который принимает сокращённые формы `orb` / `akaze` / `phase`; эти две команды не являются взаимозаменяемыми при использовании данного флага. |
| `--model {translation, rigid, affine, homography}` | `affine` | Трансформация модель для подгонки. |
| `--frames N` | `1` | Синхронизированные снимки кадров для усреднения. |
| `--reference SN` | главная | Серийный номер эталонной камеры; каждый второй элемент привязанна неё. |
| `--max-features N` | `5000` | Ограничение количества признаков ORB. |
| `--ratio-threshold F` | `0.75` | Тест коэффициента Лоу . |
| `--ransac-threshold-px F` | `3.0` | Пороговое значение для внутренних точек RANSAC. |
| `--min-matches N` | `15` | **Контроль качества** — отклонить решение, если количество совпадений с внутренними точками ниже этого значения. |
| `--max-reproj-err-px F` | `4.0` | **Пороговое значение качества** — отклонить решение, если среднеквадратичная ошибка репроекции превышает это значение. |
| `--checkerboard RxC` | — | Геометрия платы для `--method checkerboard`, например, `9x6`. |
| `--name PROFILE` | пусто | Имя профиля, встроенное в сохраненный файл JSON. **Не имя массива** — это позиционный `NAME`. |

Два контрольных порога качества являются причиной, по которой калибровка может успешно завершиться, но при этом
быть отклонена при сохранении: профиль, не прошедший хотя бы один из них, будет незаметно приводить к неверной регистрации всех
последующих захватов, поэтому его отклоняют, а не сохраняют.

`project run RECIPE.yaml` принимает файл в формате YAML или JSON, описывающий последовательность действий:

```yaml
# recipe.yaml
overrides:
  cameras:
    FrontLeft:
      exposure_us: 5000
      target_brightness: 80

stop_on_error: true
actions:
  - apply:
      name: FrontLeft
      settings:
        exposure_auto: "Off"
        gain: 6.0
        gain_auto: "Off"
  - wait: 2s
  - capture:
      name: FrontLeft
      output: pose_a/
      format: tiff
  - stream:
      name: main_rig
      count: 60
      fps: 5
      output: stream/
  - burst:
      name: main_rig
      count: 10
      interval: 0.5
      output: burst_a/
      format: tiff
  - sensor:
      name: Sky
      action: read
```

Поддерживаемые действия: `apply`, `wait`, `capture`, `stream`, `burst`, `sensor`. Действие `burst` принимает следующие параметры: `name` (обязательный), `count` (по умолчанию 5), `interval` (секунд, по умолчанию 0), `output`, `format` и `settings` (такая же структура настроек для каждой камеры, как у `apply`); серии снимков массива используют тот же механизм контроля свежесинхронизированной группы, что и `project burst`.

Запустите:

```bash
chloros-cli project run "/path/to/project" recipe.yaml

# Dry-run to validate without firing hardware
chloros-cli project run "/path/to/project" recipe.yaml --dry-run
```

## Переменные среды

| Переменная | Эффект |
| --- | --- |
| `CHLOROS_BACKEND_URL` | Переопределяет бэкенд URL (по умолчанию `http://127.0.0.1:5000`) — **учитывается только семействами команд `lattice`, `project`, и `daq pool-*`.** Основные команды (`process`, `login`, `logout`, `status`, `export-status`, `time-sync`, `selftest`) фиксируют значение `http://127.0.0.1:<port>` и игнорируют эту переменную (литерал IPv4 обходит Windows `localhost`→`::1` штраф в ~2 с на запрос), поэтому они всегда нацелены на локальную машину. |
| `CHLOROS_ARRAY_ALLOW_OVERSUBSCRIBED` | `1` понижает уровень отказа в подключении из-за переподписки массива (совокупный спрос на камеру &gt; безопасный для коллизий предел канала с `pin_resolution`) до громкого предупреждение с продолжением обработки, допуская потерю пакетов GVSP. Используется только в тестовых условиях — см. [Модель fps и пакетных потоков массива](#array-fps--burst-model). |
| `CHLOROS_CLI_MODE` | Устанавливается самим CLI; указывает бэкенду включить параллельную обработку. |
| `CHLOROS_GVSP_PROBE_FALLBACK` | `0` пропускает проверку перехода на резервный режим GVSP (только результаты ICMP). **Это отключает поддержку jumbo, а не просто подавляет сообщения в журнале** — камера отвечает на пинги DF только до 1500 на каждом пути, поэтому этот тест — единственное средство, способное обнаружить поддержку пакетов jumbo. Экономит ~1 с на каждую камеру при каждом подключении; тратит ~1,45× от максимальной пропускной способности канала, если сеть *могла бы* передавать пакеты jumbo. При установке этого параметра выводится предупреждение в журнале SDK. |
| `CHLOROS_GVSP_PACKET_SIZE_FORCE` | Зафиксировать размер пакета GVSP на N байт; полностью пропускает зондирование. Предпочтительнее использовать для каждой команды (`CHLOROS_GVSP_PACKET_SIZE_FORCE=9000 chloros-cli …`) , а не устанавливать его постоянно: зафиксированный размер перестаёт адаптироваться к сетью, находящейся перед ним, и фиксация значения 9000 на пути, который не может передавать пакеты jumbo, приводит к тому, что **каждый** захват завершается тайм-аутом с кодом `SC_ERR_TIMEOUT -1011`. |
| `TMPDIR` (Linux) | Переопределить каталог извлечения onefile в Nuitka. CLI автоматически использует `/mnt/ssd/tmp`, если он присутствует. |

## Рекомендации по устранению неполадок

- **«Требуется вход в систему»** → Запустите команду `chloros-cli login EMAIL PASSWORD` один раз на этом компьютере.
- **«backend недоступен»** → Запустите настольное приложение Chloros или запустите бинарный файл бэкэнда напрямую (`chloros-backend`), либо проверьте `CHLOROS_BACKEND_URL` в случае удаленного доступа.
- **Команды `lattice` завершаются с ошибкой «Не найдены драйверы камеры LATTICE»** → Среда выполнения Arena SDK не; пакет CLI поставляется с `win32api`, доступным на сайте Windows, но среда выполнения C входит в состав графического установщика.
- **В окнах «Подключение массива» / «Настройки массива» отображается сообщение «FRAMES WILL DROP» или «Reduce ROI to enable»** → Кольцо приёма сетевой карты хоста слишком мало (обычно сбрасывается до 32 после обновления драйвера сетевой карты). См. [Настройка и оптимизация сетевой карты хоста](#host-nic-setup--tuning-lattice-arrays) — установите параметры `ReceiveBufferLen=256`, `PendingReceives=64`.
- **Компьютер зависает при перезапуске/выключении, затем возникает ошибка WMI `Invalid class` / сетевая карта не включается / отсутствуют USB-накопители** → Устаревший драйвер USB-адаптера 10 Гбит/с вызывает ошибку `DRIVER_POWER_STATE_FAILURE` (синий экран смерти `0x9F`). Обновите драйвер адаптера — см. [Настройка и оптимизация сетевой карты хоста](#host-nic-setup--tuning-lattice-arrays).
- **Предупреждение о подкачке Jetson** → Добавьте файловый своп; файл «CLI» содержит точные команды `fallocate` / `swapon`.
- **Отсутствуют прямые команды DAQ** → Ожидаемое поведение: поставляемый пакет `chloros-cli` намеренно исключает `daq`, поэтому присутствует только `pool-*` (на PyPI SDK его тоже нет). Используйте `pool-*`, который управляет тем же датчиком через бэкэнд, или `chloros_sdk.connect_daq_sensor()` с Python.
