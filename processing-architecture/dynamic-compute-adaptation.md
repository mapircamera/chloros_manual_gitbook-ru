# Динамическая адаптация вычислений В версии

Chloros 1.3.0 используется функция определения аппаратного обеспечения и автоматический выбор стратегии обработки. Механизм обработки адаптируется к вашему оборудованию — от Jetson Orin Nano до рабочей станции с несколькими графическими процессорами — без какой-либо ручной настройки.

***

## Как это работает

При запуске Chloros выполняет профилирование вашей системы:

1. **Определяет операционную систему** — Windows или Linux
2. **Определяет ядра ЦП и общий объём ОЗУ**

3.**Определяет наличие графического процессора** — поддержку NVIDIA CUDA, объём видеопамяти (VRAM), модель
4. **Определяет модель Jetson** (если применимо) — через `/proc/device-tree/model`
5. **Проверяет датчики температуры** (Jetson) — для обработки с учётом температурных условий
6. **Выбирает стратегию вычислений** — на основе всех обнаруженных аппаратных ресурсов
7. **Автоматически настраивает количество рабочих процессов, тип конвейера и распределение памяти**

Обнаруженный профиль кэшируется для данной сессии в памяти и на диске, благодаря чему последующие запуски начинаются быстрее:

| Платформа | Кэшированный профиль |
| --- | --- |
| **Linux / Jetson** | `~/.config/chloros/system_config.json` (учитывает `XDG_CONFIG_HOME`) |
| **Windows** | `%LOCALAPPDATA%\Chloros\config\system_config.json` |

Удалите этот файл, чтобы заставить систему выполнить новое обнаружение — это полезно после добавления графического процессора (GPU) или увеличения объёма оперативной памяти. Chloros также автоматически выполняет повторное обнаружение, если кэш был записан несовместимой старой версией.

***

## Стратегии вычислений

Chloros выбирает одну из трёх стратегий вычислений в зависимости от вашего оборудования:

| Стратегия | Выбирается, когда | Рабочие процессы | Исполнитель | Конвейер |
| --- | --- | --- | --- | --- |
| **`GPU_PARALLEL`**| Графический процессор CUDA с**12 ГБ и более видеопамяти**(в унифицированной памяти Jetson, также требуется не менее 12 ГБ общей общей оперативной памяти) | `min(4, ⌊(VRAM − 0.5GB) × 0.9 ÷ 3.5GB⌋)`, минимум 2 —**ограничено до 2 на Jetson** | Рабочие процессы (отдельные контексты CUDA) | `fused_gpu` |
| **`GPU_SINGLE`**| CUDA-GPU с**2–12 ГБ VRAM**| 3 (перекрытие ввода-вывода; доступ к GPU сериализуется семафором).**1 (последовательно) на Jetson с объёмом ОЗУ менее 12 ГБ** | Рабочие процессы (отдельные контексты CUDA); последовательное выполнение внутри процесса на Jetson с небольшим объёмом ОЗУ | `fused_gpu` / `tiled_gpu` |
| **`CPU_PARALLEL`** | Без CUDA-графического процессора или с объёмом видеопамяти менее 2 ГБ | `max(2, physical cores − 1)` | `ThreadPoolExecutor` | `cpu_fallback` |

Примеры расчёта формулы количества рабочих процессов `GPU_PARALLEL`: 12 ГБ видеопамяти → 2 рабочих процесса, 16 ГБ → 3 рабочих процесса, 20 ГБ и более → 4 рабочих процесса. Каждому рабочему процессу выделяется 3,5 ГБ — это расчётная потребность задачи с поддержкой текстур — в пределах 90 % от объёма VRAM, оставшегося после выделения резерва в 0,5 ГБ.

{% hint style="info" %}
**Для стратегий использования GPU требуется версия PyTorch, поддерживающая CUDA.** Устройство, на котором установлен PyTorch без доступного CUDA-устройства, получает значение `CPU_PARALLEL`, независимо от типа его GPU. Пакет Jetson версии 1.3.0 использует сборку PyTorch для CUDA из JetPack 6, поэтому Jetson соответствует требованиям после установки библиотек CUDA и cuDNN из JetPack. Jetson с объёмом ОЗУ менее 12 ГБ всегда обрабатывает по одному изображению за раз, в процессе работы (регистрируется как `GPU_SINGLE`).
{% endhint %}

Стратегии с использованием GPU запускают пул рабочих процессов, каждый из которых представляет собой отдельный процесс ОС со своим собственным контекстом CUDA; Chloros запускает их, повторно запуская свою собственную установленную бэкенд-программу (а не через `multiprocessing` в Python, запуск рабочих процессов которого не работает внутри упакованного приложения). Стратегия на CPU использует пул потоков (Python `ThreadPoolExecutor`). Chloros не использует никаких сторонних фреймворков для распределённых вычислений (таких как Ray).

### Типы конвейеров

* **`fused_gpu`** — Полный путь обработки на GPU. Операции дебайеризации, коррекции и индексирования выполняются на GPU за один объединенный проход. Максимальная пропускная способность, требует наибольшего объема VRAM.
* **`tiled_gpu`** — Конфигурация с эффективным использованием памяти GPU. Обрабатывает изображения по частям, чтобы уместить их в ограниченную память GPU. Меньшая пропускная способность, но работает на устройствах с ограниченным объемом памяти.
* **`cpu_fallback`** — Обработка исключительно на ЦП с использованием многопоточного параллелизма. Используется при отсутствии графического процессора NVIDIA, а также в качестве крайней меры при сбое обоих конвейеров на графическом процессоре.

Цепочка резервных вариантов во время выполнения всегда выглядит следующим образом: `fused_gpu` → `tiled_gpu` → `cpu_fallback`.

## Ручная переопределение стратегии

Установите переменную среды `CHLOROS_STRATEGY`, чтобы принудительно запустить определённую стратегию — это экспертный «аварийный выход» на случай, если автоматическое определение выберет что-то неподходящее для вашей ситуации (например, чтобы оставить графический процессор свободным для других задач):

```bash
# Valid values: CPU_PARALLEL, GPU_SINGLE, GPU_PARALLEL
CHLOROS_STRATEGY=CPU_PARALLEL chloros-cli process ~/datasets/flight001
```

При сопоставлении переменной не учитывается регистр; всё, что не является одним из этих трёх имён, игнорируется, и автоматическое определение продолжается в обычном режиме. При переопределении Chloros всё равно выбирает количество рабочих процессов за вас:

| Переопределение | Используемое количество рабочих процессов |
| --- | --- |
| `CPU_PARALLEL` | `max(2, physical cores − 1)` |
| `GPU_SINGLE` | 3 |
| `GPU_PARALLEL` | `min(4, physical cores)` |

Переопределение `GPU_SINGLE` или `GPU_PARALLEL` на машине без доступного устройства CUDA отклоняется с записью `[STRATEGY]` в журнале, и в запуске используется `CPU_PARALLEL`.

Рекомендуется настраивать это для каждой команды, а не постоянно, чтобы обычные запуски продолжали автоматически адаптироваться.

## Поведение, зависящее от платформы

| Платформа | Стратегия | Рабочие процессы | Конвейер | Примечания |
| --- | --- | --- | --- | --- |
| **Jetson Orin Nano 8 ГБ** | `GPU_SINGLE` | 1 | `tiled_gpu` (последовательный) | Режим эффективного использования памяти, по одному образу за раз |
| **Jetson Orin NX 8 ГБ** | `GPU_SINGLE` | 1 | `tiled_gpu` (последовательная) | Общий объем ОЗУ менее 12 ГБ, что вынуждает использовать последовательную обработку |
| **Jetson Orin NX 16 ГБ** | `GPU_PARALLEL` | 2 | `fused_gpu` (параллельная) | Рекомендуемое периферийное устройство — ограничение Jetson: 2 рабочих процесса |
| **Jetson AGX Orin 32–64 ГБ** | `GPU_PARALLEL` | 2 | `fused_gpu` (параллельная) | Максимальная производительность на периферии (также ограничено Jetson до 2 рабочих процессов) |
| **Настольный компьютер с графическим процессором 8 ГБ** | `GPU_SINGLE` | 3 | `fused_gpu` / `tiled_gpu` | 3 рабочих процесса перекрывают операции ввода-вывода, в то время как семафор сериализует доступ к графическому процессору |
| **Настольный компьютер с графическим процессором объёмом 12 ГБ и более** | `GPU_PARALLEL` | 2–4 | `fused_gpu` (одновременных) | Оптимальная производительность настольного ПК: 12 ГБ → 2 рабочих процесса, 16 ГБ → 3, 20 ГБ и более → 4 |
| **Система только с ЦП** | `CPU_PARALLEL` | количество физических ядер − 1 (мин. 2) | `cpu_fallback` | ГП не требуется, используется пул потоков |

{% hint style="info" %}
**Единая память Jetson**: устройства Jetson совместно используют память графического процессора и ЦП. Устройство Jetson Orin NX с 16 ГБ памяти показывает ~15,3 ГБ видеопамяти (VRAM), но это та же физическая оперативная память, которую используют ОС и процессы ЦП. Именно поэтому устройства Jetson с объёмом памяти 16 ГБ и более подходят для `GPU_PARALLEL` так же, как настольные графические процессоры с объёмом 12 ГБ и более, но при этом ограничены двумя рабочими процессами — графический процессор, рабочие процессы и их контексты CUDA для каждого рабочего процесса используют один и тот же общий пул.
{% endhint %}

### Бюджет графического процессора в зависимости от объёма VRAM (дискретные графические процессоры)

На хостах x86_64 с дискретным графическим процессором NVIDIA обнаруженный объём VRAM также определяет, какой объём памяти может задействовать карта для обработки, и до какого размера могут увеличиваться пакеты:

| Объем обнаруженной VRAM | Верхний предел бюджета GPU | Коэффициент размера пакета |
| --- | --- | --- |
| **8 ГБ и более** | 90 % | ×2,0 |
| **6–8 ГБ** | 85 % | ×1,75 |
| **3,5–6 ГБ** | 80 % | ×1,5 |
| **2–3,5 ГБ** | 75 % | ×1,25 |
| **Менее 2 ГБ** | 70 % | ×1,0 |

Дискретные графические процессоры резервируют для системы всего 0,5 ГБ, поскольку они не используют системную оперативную память. Профили Jetson резервируют гораздо больше и устанавливают более низкие ограничения — см. [Руководство по NVIDIA Jetson](../linux/nvidia-jetson-guide.md#per-model-gpu-budget).

## Динамическое распределение памяти графического процессора

Chloros использует [4-потоковый конвейер обработки](processing-pipeline.md):

* **Поток 1** (Обнаружение) — Загрузка изображения, анализ EXIF, обнаружение объекта
* **Поток 2** (Калибровка) — вычисления калибровки коэффициента отражения
* **Поток 3** (Обработка) — дебайеризация на GPU, коррекция виньетирования, вычисление индекса
* **Поток 4** (Экспорт) — запись файлов, встраивание метаданных

Потоки 1, 2 и 4 потребляют мало ресурсов GPU; поток 3 — наиболее ресурсоемкий. По мере завершения работы предыдущих потоков конвейера их ресурсы графического процессора **перераспределяются между оставшимися активными потоками**, поэтому поток 3 получает всё больше памяти по мере продвижения процесса.

### Этапы распределения ресурсов

| Этап | Активные потоки | Распределение памяти графического процессора |
| --- | --- | --- |
| **Начальная** | 1, 2, 3, 4 | Распределяется между всеми потоками, большая часть — потоку 3 |
| **Средне-начальная** | 2, 3, 4 | Доля потока 1 перераспределяется |
| **Середина-конец** | 3, 4 | Доли потоков 1 и 2 перераспределяются между потоками 3 и 4 |
| **Конец** | 3 или 4 | Последний активный поток получает максимальный объём выделенной памяти |

Эти цифры определяются двумя правилами:

* Поток, являющийся **единственным** активным, получает максимальный объём выделения, заданный в его профиле.
* Когда активны несколько *ресурсоёмких* задач GPU, базовый объём выделения каждой из них распределяется между ними (ни в коем случае не опускаясь ниже заданного минимума).

Значение, фактически используемое во время выполнения, является **меньшим** из двух: выделенного объёма в профиле платформы и текущей рекомендации монитора памяти GPU, поэтому загруженная карта всегда имеет приоритет над оптимистичным профилем.

## Обработка с учётом текстур

Дебайер с поддержкой текстур (**только Chloros+** — `--debayer texture-aware`) запускает модель удаления шума на основе ИИ/машинного обучения, которой требуется примерно 1,75 ГБ VRAM в формате FP16 на каждую копию, поэтому он использует гораздо больше памяти GPU, чем стандартный метод:

* Системы с **менее 7 ГБ VRAM**обрабатывают «с учётом текстур» в**синхронном цикле, по одному изображению за раз** — несколько копий модели не помещаются, а пул рабочих процессов только усугубил бы конфликт доступа
* Системы с **7 ГБ и более VRAM** могут обрабатывать Texture Aware параллельно, хотя и с меньшим количеством рабочих процессов по сравнению со стандартным методом
* На **Jetson** обработка с учетом текстур всегда привязана к одному рабочему процессу
* При **отсутствии доступного графического процессора с поддержкой CUDA** выполняется стандартный дебайеризатор, а бэкенд записывает в журнал одну строку `[DEBAYER] … needs a CUDA GPU …` с объяснением причины
* На энергоэффективных устройствах Jetson (Nano, Orin Nano) интерфейс CLI накладывает ограничение на частоту GPU при запросе режима «Texture Aware» — см. [Руководство по NVIDIA Jetson](../linux/nvidia-jetson-guide.md#gpu-frequency-cap-for-texture-aware-on-nano-and-orin-nano)

## Управление тепловым режимом (Jetson)

Устройства Jetson имеют ограничения по температуре, особенно при размещении в закрытых помещениях или на борту летательных аппаратов. Chloros отслеживает данные встроенных датчиков температуры Jetson и автоматически масштабирует размеры пакетов:

| Температура | Реакция |
| --- | --- |
| **< 70 °C** | Нормальная работа — полная скорость |
| **70 °C** (Предупреждение) | Размер пакеты постепенно уменьшается (100 % → 50 % в диапазоне от 70 °C до 80 °C) |
| **80 °C** (Критический уровень) | Агрессивное ограничение производительности (с 50 % до 0 % в диапазоне от 80 °C до 90 °C) |
| **90 °C** (Отключение) | Полная остановка обработки на GPU |

На настольных системах с адекватным охлаждением термическое ограничение производительности срабатывает редко.

## Управление нагрузкой на память

Программа Chloros постоянно отслеживает состояние памяти графического процессора во время обработки и реагирует на трёх уровнях.

**Размер пакета.** Партия начинается с 8 изображений, умноженных на множитель платформы из приведённых выше таблиц. Затем Chloros проверяет объём свободной VRAM, резервирует 20 % её для собственных накладных расходов PyTorch и исходит из того, что на каждое изображение размером 12 МП требуется примерно 100 МБ памяти графического процессора — размер партии определяется меньшим из двух значений: ограничением, вытекающим из объёма памяти, или базовым значением для платформы. Он никогда не опускается ниже 1.

**Превентивное уменьшение.**При**загрузке VRAM выше 85%** размеры партий уменьшаются до того, как возникнут сбои.**Сокращение выделения ресурсов на каждый поток.** По мере роста текущей загрузки бюджет GPU для каждого потока сокращается: до 0,75 при загрузке выше 80 %, до 0,5 — при загрузке выше 90 %. Диапазоны мониторинга составляют 70 % (консервативный), 85 % (нормальный рабочий предел) и 95 % (риск нехватки памяти).**Отступление и восстановление при нехватке памяти.** Если событие нехватки памяти всё же происходит:

* размер пакетной обработки **уменьшается вдвое**, а при каждом последующем событии OOM — ещё вдвое; каждый последующий успешный пакет отменяет это ограничение на один шаг
* выделение памяти для активных потоков сокращается до 70 % от текущего значения, и аллокатор переключается на консервативную стратегию, снова ослабляя ограничения после серии успешных выделений
* при сильной нагрузке конвейер переключается с `fused_gpu` на `tiled_gpu`, а в крайнем случае — на `cpu_fallback`

**Оперативная память хоста (Jetson).** Перед обработкой CLI оценивает пиковый объем памяти хоста на основе количества изображений и режима дебайеризации и выдает предупреждение, если объема ОЗУ и файлового свопа, вероятно, будет недостаточно, выводя точные команды для добавления свопа — см. [Руководство по NVIDIA Jetson](../linux/nvidia-jetson-guide.md#swap-warning-and-recommendations).

## Мониторинг адаптации вычислительного уровня

### Диагностика системы

`chloros-cli selftest` — это самый быстрый способ проверить, что видит вычислительный уровень:

```bash
chloros-cli selftest
```

Его 7 проверок охватывают версию, доступность портов, запуск бэкэнда, `/api/test`, системную информацию, наличие модели шумоподавителя и готовность CUDA + шумоподавителя. Проверка 5 выводит строку с информацией об аппаратном обеспечении напрямую:

```
      GPU: NVIDIA RTX A4000, CUDA: True, PyTorch: 2.7.0
```

Проверка 7 выводит `CUDA: <bool>, Denoiser: <bool>` — оба условия должны выполняться, чтобы функция Texture Aware вообще могла использоваться.

### Журналы бэкэнда

Стратегия и количество рабочих процессов выбираются внутри бэкенда в начале каждого запуска — в командной строке (CLI) нет баннера, который бы их отображал. Когда что-то ведёт себя непредсказуемо (переход на резервный путь GPU, нехватка памяти (OOM), невозможность загрузки шумоподавителя), это отображается в журнале бэкенда для данной сессии:

| Платформа | Расположение журнала |
| --- | --- |
| **Linux / Jetson** | `~/.cache/chloros/logs/backend_<YYYYMMDD_HHMMSS>.log` (один файл на каждый запуск) |
| **Linux, бэкенд, запущенный через CLI** | также `~/.chloros/backend.log` |
| **Windows** | `%LOCALAPPDATA%\Chloros\logs\` |

### Отображение хода выполнения в реальном времени

Во время выполнения CLI отображает текущий прогресс по каждому потоку (обнаружение, анализ, обработка, экспорт), передаваемый через Server-Sent Events — это позволяет на практике определить, является ли поток 3 узким местом. См. [Конвейер обработки](processing-pipeline.md).
