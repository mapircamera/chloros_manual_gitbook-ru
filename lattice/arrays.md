# Многокамерные массивы

**Массив**LATTICE представляет собой две или более камер LATTICE, соединенных в единый синхронизированный блок. Одна из камер выступает в роли**ведущей**: она подает аппаратный триггерный импульс GPIO на общую линию синхронизации (по умолчанию**Line2**), благодаря чему все камеры фиксируют один и тот же момент времени. Chloros добавляет синхронизацию времени по протоколу PTP, предварительный просмотр в реальном времени (в виде отдельных фрагментов для каждой камеры или единого выровненного многополосного композитного изображения) и синхронизированную съемку — каждый цикл съемки формирует одну**группу кадров**, в которой все камеры имеют одинаковую временную метку и идентификатор кадра (отображается как `fid:N` на выходе съёмки).

Массивы — это способ, с помощью которого монохромные (M3M) камеры формируют растительные индексы: одна камера предоставляет один диапазон, а массив выравнивает их в многодиапазонный стек. См. [Монохромные камеры и растительные индексы](mono-indices.md).

Существует три равнозначных способа подключения массива, и все они запускают один и тот же поток «smart-prep»:

| Поверхность | Точка входа |
| --- | --- |
| Графический интерфейс | Вкладка «Камеры» → **Подключить массив** (синяя кнопка) |
| CLI | `chloros-cli lattice array-connect --serials SN1,SN2,…` (первый по порядку = ведущий) |
| Python SDK | `connect_array(serials=[…])` → `ArraySession` (первый серийный номер = ведущий) |

Smart-prep выполняет в следующем порядке: проверку сетевых возможностей (ICMP DF ping + GVSP-проба), выбор уровня синхронизации, автоматическое уменьшение размера кадра для адаптации к кабелю, включение PTP, автоматический выбор формата пикселей для каждой камеры, начальную настройку автоэкспозиции на основе сохраненного состояния каждой камеры и настройку триггера GPIO на линии Line2.

{% hint style="info" %}
Камеры должны быть доступны по каналу связи, прежде чем что-либо из вышеперечисленного начнёт работать — см. раздел [Подключение камер](connecting.md) для информации об обнаружении, адресации и загрузке калибровочных данных при первом подключении. Для многокамерных установок настройки кольца приёма сетевой карты хоста имеют такое же значение, как и скорость канала связи; полная таблица «симптом→исправление» приведена в [CLI Справочник § Настройка и оптимизация сетевой карты хоста](../reference/cli-reference.md#host-nic-setup--tuning-lattice-arrays).
{% endhint %}

## Диалоговое окно «Подключение массива»

Вкладка «Камеры» → **«Подключить массив»**открывает мастер из трёх шагов:**«Выбрать» → «Режим отображения» → «Настройки»**.

### Шаг 1 — Выбор ведущей и ведомых

<!-- SCREENSHOT-NEEDED: Array Connect dialog, Select scene, with 3-4 LATTICE cameras discovered. Table showing Camera / Serial / IP / Master radio / Slave checkbox columns, with the green "GPIO master detected — selections pre-populated" probe banner visible above the table. -->

камер Как только диалоговое окно открывается, оно начинает сканировать сеть («Сканирование сети...»), а затем проверяет подключение триггера GPIO («Проверка подключения GPIO...»). Для создания массива требуется как минимум **2 камеры**.

Проверка подключения, по возможности, предварительно заполняет поля выбора ролей и отображает один из трёх баннеров:

| Баннер | Значение |
| --- | --- |
| «Обнаружен ведущий GPIO — выбор предварительно заполнен» (зелёный) | Проверка обнаружила топологию триггера; флажки «Ведущий» и «Подчинённые» уже установлены. |
| «Мастер не обнаружен — проверьте кабель GPIO» (оранжевый) | Ни одна камера не уловила импульс запуска; проверьте синхронизирующие кабели. Вы по-прежнему можете выбрать роли вручную. |
| «Отсутствует синхронизирующий кабель: {serials}» (оранжевый) | У перечисленных камер не подключен синхронизирующий кабель. |

Таблица камер содержит столбцы **Камера / Последовательный порт / IP / Мастер (радиокнопка) / Ведомая (флажок)**:

* Выберите ровно **одного мастера**и**одну или несколько ведомых камер**. Повторное нажатие на радиокнопку текущего мастера сбрасывает его выбор.
* Камеру с пометкой **«Нет кабеля синхронизации»** нельзя выбрать в качестве ведомой — ведомая камера без проводов запуска будет бесконечно ждать сигнала по линии синхронизации и передавать нерабочий сигнал. Вместо этого подключите эту камеру в автономном режиме.
* Камеры, уже подключённые в автономном режиме, *не* отключаются: подключение к массиву освобождает автономную сессию и вновь открывает камеру внутри массива.

**Далее: Режим отображения →**становится доступным после выбора одного ведущего устройства и как минимум одного ведомого.**Повторное сканирование** запускает повторный поиск устройств и проверку подключений.

{% hint style="warning" %}
Кнопка **«Отмена»** отключена во время сканирования или проверки — отмена в середине проверки может привести к сбою камеры SDK на прошивке камеры LATTICE. Дождитесь завершения индикатора загрузки.
{% endhint %}

### Шаг 3 — Настройки массива и прогнозируемый результат

<!-- SCREENSHOT-NEEDED: Array Connect dialog, Settings scene, healthy state: left column with ROI / Binning / Pin resolution / Trigger Rate controls, right "Projected Outcome" column showing green "Simultaneous capture" tier, an fps range, the NIC line, the "Sim-emit burst" line, and the "Wire budget" line with a checkmark. -->

При входе в эту сцену Chloros запрашивает у бэкэнда **рекомендацию**и автоматически применяет комбинацию области интереса (ROI) и биннинга, подходящую для приемного кольца вашего NIC (система отдаёт предпочтение биннингу перед кадрированием ROI, поскольку биннинг сохраняет полное поле обзора). Каждое внесенное вами изменение запускает повторный анализ в режиме реального времени и обновляет панель**Прогнозируемый результат** справа.

Левая колонка — настройки:

| Элемент управления | Варианты | По умолчанию | Примечания |
| --- | --- | --- | --- |
| **ROI (поле зрения)** | Полное (2048×1536) / Половина (1024×768) / Четверть (512×384) | Полное | Кадрирование датчика: кадрирование до половины или четверти для получения меньшей области с исходным шагом пикселей. |
| **Биннинг** | 1× / 2× (сумма 2×2) / 4× (сумма 4×4) | 1× | Аппаратный биннинг: 2×2 = полное поле зрения при четверти затрат на считывание; 4×4 = полное поле зрения при 1/16. Скрыто, если камеры не поддерживают биннинг. |
| **Изображение на линии передачи** (считывание) | — | — | Ширина × высота после биннинга, фактически отправляемая по линии передачи, округлена до кратных 16 (минимум 64). |
| **Разрешение по выводам**| флажок | выкл. | Chloros обычно автоматически активирует биннинг при подключении, когда прогнозируемая скорость падает ниже**1,5 кадров в секунду**. Фиксация сохраняет выбранный вами размер кадра и принимает более низкую скорость передачи — и превращает конфигурацию с избыточной пропускной способностью в жесткий отказ в подключении вместо автоматического снижения скорости. |
| **Частота триггера** | 0,5–60 кадров в секунду, шаг 0,1 | пусто = авто | Частота срабатывания триггера ведущего устройства. Оставьте поле пустым, чтобы Chloros рассчитал её самостоятельно. |
| **Пропускная способность кабеля**| 20–2000 МБ/с, шаг 10 | пусто = авто | Фактическая пропускная способность хоста в МБ/с —**единственное значение, от которого зависит распределение всего массива.** Определяется автоматически по сетевому адаптеру. Уменьшите это значение, если массив сообщает о повреждённых кадрах: обнаруженное значение завышает возможности USB-адаптеров и общих коммутаторов. Изменение этого параметра приводит к повторному запуску прогнозирования в режиме реального времени. |

Правая колонка — **Прогнозируемый результат**:

* **Уровень синхронизации** — «Одновременная съёмка» (зелёный), «Одновременная съёмка (поэтапная передача FTD)» (зелёный), «Поэтапная съёмка (смещение 100 мс)» (янтарный) или «Конфигурация слишком велика» (красный).
* **Прогноз fps** — отображается в виде диапазона («тускло → ярко»), поскольку частота синхронизированной матрицы ограничивается выдержкой самой медленной камеры.
* **Строка сетевой карты** — скорость соединения и устойчивая пропускная способность («NIC {mbps} Мбит/с · устойчивая {N} МБ/с»).
* **Проверка пакетного вывода Sim-emit** — может ли кольцевой канал сетевой карты хоста принять один одновременный пакетный вывод со всех камер («Пакетный вывод Sim-emit: X МБ · доступный объем кольца сетевой карты: Y МБ ✓/✗»).
* **Проверка пропускной способности кабеля** — сопоставление совокупного спроса в стационарном режиме и безопасного для предотвращения коллизий предельного значения пропускной способности кабеля («Пропускная способность кабеля: {demand} МБ/с, требуемая {n} камерами · предельное значение {ceiling} МБ/с ✓/✗ превышение пропускной способности»).
* **«Максимальное количество камер на этом канале: {n} — устанавливается минимальным значением пропускной способности на камеру, поэтому объединение в группы не увеличивает это значение»** — отображается, когда вы приближаетесь к предельному количеству камер (или превышаете его).
* **«При таких настройках КАДРЫ БУДУТ ПРОПУСКАТЬСЯ»**— красное предупреждение с указанием причины со стороны бэкенда, а также списком препятствий и синими**рекомендациями по устранению** («Чтобы уместить этот массив в сеть» / «Чтобы разблокировать одновременную съемку»).

Кнопка **«Применить и подключиться»** заблокирована до тех пор, пока не будет сформирован прогноз, а её надпись объясняет причину отказа:

| Надпись кнопки | Значение | Что действительно поможет |
| --- | --- | --- |
| «Анализ...» | Анализ ещё не завершён. | Подождите. |
| **«Слишком много камер для этой сети»**| Массив перегружает канал (проверка совокупной пропускной способности завершилась неудачно). | Уменьшите количество камер, включите поддержку джамбо-фреймов по всей цепочке или установите более быструю сетевую карту.**Уменьшение области интереса (ROI) НЕ поможет** — см. ниже. |
| **«Уменьшите ROI, чтобы включить»** | При этих настройках кадры будут пропадать (проверка пакетных потоков/кольца не прошла). | Уменьшите ROI, увеличьте биннинг или исправьте кольцо приёма сетевой карты. |

Во время подключения может появиться зелёная **панель загрузки калиброчных данных** с индикатором прогресса для каждого последовательного порта: при первом подключении камеры к компьютеру Chloros загружает из камеры пакет заводских калиброчных данных объёмом ~3,8 МБ по GigE (примерно 70 секунд на камеру). Для камер, находящихся в кэше, эта панель не отображается. См. [Подключение камер](connecting.md).

## Пропускная способность: сколько камер помещается

Пропускная способность массива зависит от канала связи, а не от Chloros, поэтому расчётные данные приводятся в руководстве по оборудованию: **[Планирование пропускной способности массива](https://mapir.gitbook.io/lattice-camera/setup/array-bandwidth-planning)**.

Как Chloros обрабатывает эти данные: диалоговое окно подключения запускает проверку сети, прогнозирует достижимую частоту кадров и выбирает подходящий уровень. Если массив перегружает кабель, он отказывается подключаться, а не пропускает пакеты без уведомления — см. панель прогнозируемых результатов, описанную выше.

## Когда кадры пропадают

Камера может отсутствовать в опубликованной группе по двум совершенно разным причинам,
и для их устранения требуются противоположные меры. Chloros учитывает их отдельно, а не выдает одно
«неполное» число, не указывающее ни одну из них:

| Что произошло | Что это означает | Где искать |
| --- | --- | --- |
| **Повреждённый**— фрейм прибыл, но имел структурные повреждения | Потеря пакетов GVSP на сетевом пути |**Пропускная способность канала**, кольцо приёма сетевой карты, джамбо-фреймы, коммутатор |
| **Никогда не поступил**— фрейм не поступил вовсе | Камера не сработала или из неё ничего не вышло |**Синхронизационный кабель M8**, линия синхронизации, все ли участники системы находятся в режиме охраны |

Разделение переоценивается каждые 10 секунд во время потоковой передачи данных массива. При значении выше 5 % это
регистрируется с указанием обоих показателей, и о каждом повреждённом буфере сообщается при первом
случае для каждой камеры, затем данные суммируются раз в минуту, чтобы длинная сессия оставалась читаемой.

**Повреждённые кадры с нулевым показателем «никогда не поступали» означают, что срабатывание и синхронизация по кабелю идеальны**, а каждый потерянный кадр связан с сетевым каналом. Решением является снижение**Wire Budget** и
повторное подключение.

{% hint style="warning" %}
**Снижение частоты срабатывания не помогает при повреждённых кадрах.** Темп передачи пакетов
камеры задаётся однократно при подключении. Снижение частоты триггера изменяет частоту появления
пакетов в пакетном потоке, а не скорость, с которой сам поток передаётся по кабелю. На протестированной установке с 4 камерами
5-кратное снижение частоты триггера ничего не изменило, в то время как уменьшение «Wire Budget» с 240 до
200 МБ/с позволило снизить долю повреждённых кадров в той же системе с 10,4 % до нуля.
{% endhint %}

Работающий массив не может перепланировать себя — отключитесь и подключитесь заново, чтобы механизм выбора времени подключения
мог работать с учётом нового бюджета.

### Скорость сетевых адаптеров USB ограничена 200 МБ/с

USB-адаптер Ethernet объявляет свою скорость *Ethernet*-соединения, но то, что он может фактически
поддерживать, ограничено шиной USB и её драйвером. Раньше USB-ключу 10GbE приписывали
пропускную способность примерно 1000 МБ/с — значение, которое никто никогда не измерял, — и при синхронизации
четырёх камер с этим мнимым запасом пропускной способности повреждалось 6–18 % кадров, в то время как массив
по-прежнему показывал нормальную целевую частоту кадров. Пропускная способность адаптеров, подключаемых по USB, теперь ограничена
**200 МБ/с**. Это ограничение является абсолютным, а не процентным, поскольку пределом выступает
шина: USB-адаптер 1 Гб/с обеспечивает скорость около 80 МБ/с и не подвержен этому ограничению.

Если ваш хост действительно работает быстрее этого предела, увеличьте значение **Wire Budget**, чтобы это отразить.

## Синхронизация времени по PTP

*Синхронизация* кадров осуществляется с помощью аппаратного триггера; **PTP** (IEEE 1588 PTPv2) обеспечивает сопоставимые *метки времени* на всех устройствах. Эта функция включена по умолчанию при подключении массива:

* **Хост-бэкенд Chloros работает в качестве PTP-главного сервера**. Камеры LATTICE и световые датчики DAQ-E синхронизируются с ним в домене 0, поэтому временные метки изображений и спектры DAQ привязаны к одному такту (~1 мс).
* `--no-ptp` (CLI) отключает его для лабораторных работ — в этом случае временные метки между камерами **не** сопоставимы.
* Проверьте состояние синхронизации с помощью CLI:

```bash
chloros-cli time-sync status     # grandmaster state, clock identity
chloros-cli time-sync peers      # slaves seen (cameras + DAQ-E sensors)
chloros-cli time-sync cameras    # per-camera PtpStatus / PtpOffsetFromMaster / PtpMeanPathDelay
```

На вкладке «Камеры» нет индикатора PTP; там отображаются следующие параметры синхронизации для каждой камеры: доступные только для чтения **Роль**(ведущая/ведомая),**Линия синхронизации** и уровень возможностей массива. Состояние PTP DAQ-E отображается в сведениях о датчике на вкладке «Световые датчики».

массива в реальном времени В основной области просмотра доступны два варианта макета (переключение в верхней панели): **режим сетки**(каждая плитка представляет собой ячейку; перетаскиванием можно изменять порядок, если замок сетки разблокирован) и**режим списка**(массивы во всю ширину вверху, одна активная камера ниже). Ползунок**Feed Zoom** регулирует размер плиток; при ширине ячейки менее 200 пикселей наложения с названием и частотой кадров автоматически скрываются.**Отдельный режим** отображает по одной плитке на каждую камеру. На каждой плитке отображаются:

* название камеры (вверху слева),
* **показатель fps** (вверху справа) — это *реальная частота захвата* камеры, сообщаемая серверной частью, а не частота опроса предварительного просмотра (предварительный просмотр в реальном времени ограничен 30 fps независимо от частоты захвата),
* индикатор состояния — зелёный (трансляция) / жёлтый (загрузка) / красный (ошибка),
* **индикатор устаревшего кадра**, если в течение 2 с не поступил новый кадр — это нормально в течение ~5 с после любого подключения/отключения, пока бэкенд перераспределяет пропускную способность между камерами.**Комбинированный режим**отображает одну составную плитку: бэкенд выполняет дебайеризацию, масштабирование, выравнивание, шумоподавление, преобразование в яркость по полосам (плюс коэффициент отражения DLS, если подключен датчик освещенности), вычисляет индексный выражение массива, применяет LUT и передает результат в формате MJPEG. До тех пор, пока не будет отображен первый выровненный кадр, плитка отображает своё состояние: «Подготовка массива…», «Калибровка выравнивания…», «Ожидание первого кадра…» или — если лимит попыток автоматического выравнивания (~30 с) исчерпан — «Требуется выравнивание» с кнопкой**Калибровать выравнивание**.

Полезные сведения о комбинированном режиме:

* Композитный сигнал привязан к кадру **главной**камеры. Наведение AE-ROI и точечный экспонометр на композитном сигнале дают точные результаты для главной камеры и приблизительные — для подчиненных; используйте**Разделенный вид** (настройки массива → «Показать камеры-участницы») для получения плиток с пиксельной точностью для каждой камеры без открытия дополнительных подключений к камерам.
* **Слои отображения**(настройки массива; по умолчанию выключено) позволяют выбрать передний и задний слой — любую входящую в массив камеру или**Индекс**. При значении переднего плана = Индекс пиксели, выходящие за пределы минимального/максимального значений LUT, отображают задний слой.
* **Разрешение рендеринга** (по умолчанию 720p) задаёт высоту потокового изображения *и* размер экспортируемого композитного изображения. Изображения с каждой камеры всегда экспортируются в полном разрешении.
* Выравнивание рассчитывается для каждого сеанса и никогда не сохраняется — см. раздел «Выравнивание» на панели настроек массива, где указаны остаточные значения RMS и находится кнопка «Перекалибровать».

## Захват: мониторинг против анализа

Поверхности захвата массива чётко делятся на **уровень мониторинга**(запись того, что вы видите) и**уровень анализа** (запись необработанных данных, калибровка позже):

| Рабочий процесс | Уровень | Что сохраняется | Пользовательский интерфейс | CLI |
| --- | --- | --- | --- | --- |
| **Захват**(фотографии) | Анализ | Одна синхронизированная группа кадров на каждый проход; файлы по каждой камере на каждом выбранном уровне экспорта (сырые данные/без дебайера/яркость/отражательная способность/предварительный просмотр/индекс) + `.daq` в виде дополнительного файла | Кнопка «**Захватить всё**» + Настройки захвата | `lattice array-capture` |
| **Запись индексного видео** | Мониторинг | Отображаемый в реальном времени комбинированный индексный композит — 8-битный, разрешение предварительного просмотра, встроенная LUT; требуется открытый поток в реальном времени | ● Запись индексного видео (комбинированные массивы) | `lattice array-record` |
| **Серия необработанных кадров → построение видео**| Анализ | Необработанные кадры с датчика с полной частотой захвата + манифест + `.daq`, затем автономная реконструкция в откалиброванное видео яркости / отражательной способности / индекса, синхронизированное по времени с показаниями DAQ | ⦿ Запись серии необработанных кадров →**Построение видео** | `lattice array-burst` → `lattice array-build-video` |

Практическое правило: если пиксели будут служить источником *измерений*, используйте режим захвата или серийной съемки (для анализа); если вам просто нужно *посмотреть или продемонстрировать*, что зафиксировал массив, запишите индексированное видео (для мониторинга).

### Настройки захвата (графический интерфейс)

<!-- SCREENSHOT-NEEDED: Capture Settings pane (gear next to Capture All) with a connected array: capture-mode buttons (Single/Continuous/Interval), the bulk export-type toggle row, the Fastest Capture toggle, and the per-array group card showing the Aligned checkbox and the "Record index video" / "Record raw burst" buttons. -->

Значок шестеренки рядом с **«Захватить всё»** открывает панель «Настройки захвата» (требуется открытый проект — результаты захвата сохраняются в него):

* **Режим захвата**:**Однократный**(один проход) /**Непрерывный**(последовательно; ограничен количеством снимков (по умолчанию 1) или продолжительностью (по умолчанию 10 с)) /**Интервал** (таймлапс: N снимков через интервал X, всего Y; по умолчанию 1 снимок каждые 5 с в течение 1 минуты).
* **Типы экспорта для каждой камеры**: Raw, Debayered, Radiance, Reflectance, Preview, Index — по умолчанию включены все применимые параметры. Radiance/Reflectance скрыты для камер серии RGB-filter;**Reflectance отображается только в том случае, если камера имеет световой датчик DAQ** (собственный или унаследованный от массива); для Index требуется настроенное выражение индекса.
* **Выровненный**(для массива, по умолчанию**включено**): деформирует экспортируемые данные элементов в соответствии с профилем выравнивания массива, чтобы экспортированные данные были пиксельно-согласованы. Raw всегда остается невыровненным, но несет трансформацию в метаданных.
* **Быстрая съемка** (переключатель): только необработанные данные + назначенное значение DAQ + бесплатный композитный индекс, с пропуском калибровочных вычислений во время съемки для обеспечения максимальной скорости — восстановление яркости/отражательной способности/индекса позже из сохраненного `.daq`.
* Выделения сохраняются вместе с проектом. Скрытые или приостановленные камеры пропускаются.

Эквивалентный CLI (та же конечная точка бэкэнда, та же семантика):

```bash
# One synced group, every applicable export level per camera (the default)
chloros-cli lattice array-capture -o output/

# Interval timelapse: one reflectance pass every 10 s for 5 minutes
chloros-cli lattice array-capture --interval 10 --duration 300 --processing reflectance -o timelapse/

# Fastest grab for a moving rig — raw + .daq now, calibrate later
chloros-cli lattice array-capture --fastest -o flightline/

# 30-second monitoring clip of the combined index view, plus a GIF
chloros-cli lattice array-record --duration 30 --fps 10 --gif -o monitoring/

# 5-second analysis-grade raw burst, then build the combined index video
chloros-cli lattice array-burst --duration 5 --build --products combined:index --fps 10 -o capture/
```

Сжатие для снимков в формате TIFF осуществляется с помощью `deflate` (без потерь, по умолчанию) или `none` — полные таблицы флагов, структура папки с данными захвата и правила повторной обработки приведены в [Справочнике по CLI](../reference/cli-reference.md#capture-modes-recorders--offline-reprocess).

## Подключение датчика освещенности DAQ

Для предварительного просмотра с коррекцией отражательной способности и освещенности требуются данные о нисходящем свете от датчика DAQ (подключенного на вкладке **Датчики освещенности**):

* В **строке массива**на боковой панели отображается**кнопка «DAQ · вкл./выкл.»** — *включена*, когда установлен датчик освещенности на уровне массива **или** у любой камеры в массиве есть собственный датчик; в всплывающей подсказке указано, какой именно датчик подает данные на какую камеру.
* Назначение для всего массива осуществляется в настройках массива → **Датчик окружающего освещения**→ раскрывающийся список**Датчик освещенности**. Этот выбор сохраняется в проекте, распространяется на каждую камеру в массиве, при этом отдельные камеры по-прежнему могут переопределить его с помощью собственного датчика.
* Строка состояния ниже отображает текущее состояние: **Выкл.**→ «Ожидание первого спектра…» →**«Активно — для всех камер в массиве выполнена коррекция освещенности»** → или, если за последние 3 с не поступило нового спектра, уведомление об устаревших данных — продолжает использоваться последнее значение (значения никогда не истекают на пути захвата).

При назначенном датчике: становится доступен тип экспорта «Отражательная способность», предварительный просмотр в реальном времени корректируется с учётом освещения, прогнозируемая автоэкспозиция может использовать спектр, и при каждой съёмке по отражательной способности значение DAQ, фактически использованное при съёмке, записывается в виде **`.daq` sidecar** рядом с изображением, чтобы съёмку можно было переобработать позже.

## Параметры `array-connect` и CLI

| Флаг | По умолчанию | Описание |
| --- | --- | --- |
| `--serials SN1,SN2,…` | автоматическое обнаружение всех камер LATTICE (требуется ≥2) | **Первый по порядку — MASTER.** |
| `--line {Line0,Line2,Line3}` | `Line2` | Линия синхронизации GPIO. |
| `--target-fps F` | auto | Частота срабатывания триггера MASTER. |
| `--binning {1,2,4}` | auto | Аппаратное биннирование. |
| `--force-tier {sim-capture-sim-emit, sim-capture-ftd-stagger, slip-emit-and-capture}` | auto | Переопределение выбора уровня синхронизации экспертом. |
| `--wire-ceiling-mbps MB_PER_S` | определяется автоматически | Бюджет канала хоста в МБ/с — форма поля **Бюджет канала** в CLI. Уменьшите его, если массив сообщает о повреждённых кадрах. Сохраняется вместе с проектом, поэтому при последующем повторном подключении он восстанавливается. |
| `--no-recommend` | выкл. | Пропустить этап анализа сети. |
| `--no-ptp` | выкл. | Отключить PTP (в этом случае временные метки между камерами не будут сопоставимы). |

`lattice array-list`, `array-status` и `array-disconnect` управляют постоянным сеансом. Полный справочник по подкомандам, включая выравнивание (`align-calibrate` / `align-apply`) и сетевые инструменты, находится в разделе [CLI Справочник § chloros-cli lattice](../reference/cli-reference.md#chloros-cli-lattice); эквиваленты SDK (`connect_array`, `ArraySession`, `attach_array`, `analyze_array_network`) приведены в [SDK Справочник](../reference/sdk-reference.md). Начиная с Python бюджет проводов составляет `connect_array(..., wire_ceiling_mbps=120)`, а разбивка по «активным с ошибками» и «недоставленным» находится в [`/api/camera/array/<id>/capability`](../reference/sdk-reference.md#array-health--which-subsystem-is-losing-frames).
